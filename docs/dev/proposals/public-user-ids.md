# Public user ids

**Status:** PROPOSED (2026-11-12). Planning doc; the build runs in its own session once this is approved. Decisions D1 to D6 ruled (§ 12). Five Claude review rounds and Codex round 1 folded (§ 13).

## 1. Why

Integer user ids (`users.id`, a serial) are on the wire, web and app. Verified on 2026-11-12:

- Logged out, `GET /api/users/1, 2, 3, …` (60/min/IP, `rl:profile`) returns every account's display name: `resolveProfileViewer` answers `shell` WITH `name` for every non-public tier when there is no viewer. A 404 vs a shell also tells you whether an account exists.
- The integers give away the user count, signup order and growth.
- People + Add Friends + Scan (PR #115) shipped the profile QR and share link as `${WEB_BASE}/u/<int>` on purpose: this project replaces them.

**Goal:** the integer never leaves the server. Every user id a client sees, sends, scans or links is a random public id, and no image address points to a person.

**Not goals:** stopping a signed-in user from crawling the graph through follower lists (bounded by tiers and rate limits); the other serial ids on the wire (§ 11).

## 2. Already ruled (2026-11-12)

- A random public id in the moment-code Crockford alphabet (`docs/dev/session-codes.md`), minted at signup, backfilled, never reused.
- Not handles (guessable, squatting, impersonation, rename redirects; there is no username concept, root CLAUDE.md § Trust model). Not Hashids / Sqids (a reversible encoding of the integer, so the order leaks back).
- The public id is the ONLY user id outsiders see. Changing only the link fixes nothing while the API still accepts integers.
- Old links break on purpose: an old QR shows "This code isn’t available", an old `/u/<int>` answers 404. No redirect from the integer (it would keep the existence check alive).
- D1 to D3 of this plan (§ 12).

## 3. The id

- **Format:** 12 characters, the first one a LETTER (the 22 letters of the Crockford alphabet), the other 11 any of its 32 characters: about 59 bits. `^[A-HJKMNP-TV-Z][0-9A-HJKMNP-TV-Z]{11}$`. Letter-first means a public id can never look like an integer: an all-digit id would be caught by the app's legacy `/u/<digits>` rule and by the digits-only internal identity check (`lib/identity.ts:35`), and the leak scan (§ 9) can match `u:\d` exactly. Canonical uppercase, no hyphen (never typed, QR and links only; 12 characters can't pass for a 4- or 8-character moment code). Input is case-insensitive and otherwise strict, like `normalizeCode`. `isPublicUserId` / `normalizePublicUserId` go in `@verre/core`.
- **Minting:** 🔒 a `BEFORE INSERT` trigger ALWAYS sets `NEW.public_id := gen_public_user_id()`, whatever the insert supplied, so no creation path can choose an id (a lookalike, a deleted person's old id that their old links would then open, or a probe through the unique violation). Better Auth copies a DECLARED field from the sign-up body unless it is `input: false` (`node_modules/better-auth/dist/db/schema.mjs:62-79`); § 5 declares `publicId` with `input: false`, so a body carrying it answers 400 for a free and a taken email alike, before the duplicate check. The trigger covers every other path (raw inserts, seeds, a future writer). The column DEFAULT stays for the backfill and Prisma's declaration. The generator builds on `gen_random_uuid()` bytes (core Postgres, already used by the rehydration migrations), skipping the version and variant bytes (6 and 8). The 11 tail characters use `byte % 32` (uniform: 256 is a multiple of 32); the first uses rejection sampling (a byte below 242, then `% 22`; 242 = 11 · 22). Skipping bytes 6 and 8 leaves 14 usable bytes, so after the 11 tail characters only 3 remain to try for the first; all three are 242 or more about once in 6,000 mints, and then the function loops to a fresh `gen_random_uuid()`. The synthetic sign-up id (§ 5) uses exactly the same mapping. `search_path` pinned in the definition (the catalog fold lesson, `prisma/CLAUDE.md`).
- **Restores:** the insert trigger also fires on `COPY`, so a data-only restore would give every user a new id and break every link and QR: it needs `--disable-triggers` (runbook line in `docs/dev/deployment.md`). A full `pg_dump` restore is fine (triggers are created after the data).
- **Collisions:** `UNIQUE` (`users_public_id_key`). A clash fails that one insert loudly; the chance per signup is about N / 2^59, so no retry loop.
- **Immutable:** a `BEFORE UPDATE OF public_id` trigger rejects a change (scoped to the column, so the lifetime-counter bump on every rating doesn't fire it). The forward cache in § 4 depends on this.
- **Never reused:** integers are never reused (serial), a deleted account's public id goes with its row, and a fresh mint is random, so no retired-ids table.
- **The migration:** one file, in `BEGIN` / `COMMIT` (`scripts/check-migration-transactions.mjs`), with `SET LOCAL lock_timeout = '5s'` and the P3009 recovery note like `20261111200000_you_profile_step4` (a volatile DEFAULT on `ADD COLUMN` rewrites `users` under ACCESS EXCLUSIVE, and every authenticated request reads `users`). Contents, all additive:
  - the function, the column (`VARCHAR(12) NOT NULL DEFAULT gen_public_user_id()`: every existing row gets its own value in the same statement), the unique constraint, the format CHECK and the two triggers;
  - the three `tile_*_own_url` columns and their backfill (§ 8);
  - `follows (following_id, created_at)` and `(follower_id, created_at)`, with matching `@@index` lines in `schema.prisma` (or the `migrate diff` gate fails);
  - CHECKs on `session_bans.identity_id` and `wines.added_by_identity_id` (NULL allowed) matching the internal validator EXACTLY (`lib/identity.ts:35-37`: case-insensitive `a:` / `d:` uuids, so `~*`; `u:` any digits), so a missed inbound translation fails loudly instead of storing a ban that never matches (the grant read compares against `u:<int>`, `lib/sessionGrant.ts:45`). Before merging, count nonconforming rows in both tables AND the Redis bans sets and adder values (promotion copies those as-is, `lib/session.ts:643-645`). `scripts/check-session-record-checks.mjs` gains `wines` in its table list (it has `session_bans` but not `wines`) and `prisma/session-record-checks.json` is regenerated.
  - Lock order: the `follows` indexes and the two `ADD CONSTRAINT`s (ACCESS EXCLUSIVE on `wines` and `session_bans`, each with a scan) first, the `users` ALTER last, so its lock isn't held through the others. The pre-deploy `pg_locks` check covers all four tables.
- **Prisma:** `publicId String @unique @default(dbgenerated("gen_public_user_id()")) @map("public_id") @db.VarChar(12)`. **Better Auth:** `user.additionalFields.publicId = { type: 'string', required: false, input: false, returned: true }` (`required: true` would 400 every sign-up). The CHECKs and triggers are invisible to `migrate diff`, so the suite pins them.
- **No schema contract step:** the integer stays the primary key and every foreign key; expand and contract happen on the wire.
- **Build checks:** Prisma 7 and BA's adapter both omit the column on create (it must not be sent as NULL).

## 4. The wire boundary

**Rule:** the integer stays the internal id everywhere: Postgres keys, Redis keys, the `u:<int>` session identity, `session.user.id` inside `auth()`, `resolveUser`, rate-limit keys, the two stored identity-string columns. The public id exists only at the edge.

**Why not re-key the identity itself** (`u:<publicId>` internally): about 91 `u:` build and parse sites in `app/` + `lib/`, two stored-string columns, every rating and roster key in Redis, and SQL that builds `'u:' || user_id` inside the grant read and the rehydration. That rewrites the trust anchor and the session mutation contract. Translating at the edge changes no authorization decision.

**Trust model unchanged:** identity still comes only from the cookie or the anon token. A `u:<publicId>` on the wire is presentation, or the TARGET of an action, exactly as `u:<int>` is today.

**`lib/publicIds.ts`:**
- `publicIdsFor(userIds)` → `Map<int, publicId>`: a bounded LRU in front of one batched indexed query, entries kept 10 minutes (the mapping never changes, but an entry would otherwise outlive the account's deletion, and the miss rule below would differ by instance); 🔒 a miss is never cached.
- 🔒 **A miss is dropped, never passed through.** Integers without a users row do reach the outbound paths: a deleted account lingers in Redis identities, rating keys, bans, roles and wine provenance until the `d:` migration (a best-effort projection), and a host can ban any `u:<int>`. Such an entry leaves the payload; it never emits the integer.
- `userIdForPublicId(publicId)` → `int | null`, indexed, not cached.
- `wireIdentity` / `internalIdentity` translate `u:` (`a:` / `d:` pass through). Separate validators for the wire shape and the internal shape; the internal `isValidIdentityId` keeps `^u:\d+$`.
- `parsePublicIdParam(segment)`: **FORMAT ONLY**, 400 only for a malformed value (an integer is malformed). No database read at that point.

**Inbound** (full file:line list: `.local/public-user-ids/inventory.md`):
- Path: `/api/users/[id]` + `follow` / `badges` / `followers` / `following`, `me/blocks/[id]`, `me/mutes/[id]`, `session/[code]/bans/[identityId]`, `bans/preview/[identityId]`. Query: `/api/feed?user=`, `/api/me/sessions?hosts=&people=`. Body: `taggedUserIds`, set-role `targetId`, kick / ban `identityId`, brought-by `broughtByIdentityId`.
- 🔒 **Resolution happens where today's code meets a nonexistent integer: after the limiter and after the role gates, and a null follows exactly that path.** Moving the lookup into the parse slot (before the limiter) would answer an unknown id 400 and skip the limiter, which tells "deleted" from "blocked me" and makes a spent limiter's 429 mean "exists". The null paths: profile, badges, followers, following, `feed?user=` → 404; follow / block / mute POST → limiter charged, the same 200; their DELETEs → 200; set-role → `refuse(400, 'targetId required')` after the gates; bans POST → limiter charged, 200, nothing written; unban → 200; ban preview → 404; brought-by → "that person is not in this moment". `hosts=` with an unknown entry adds a FALSE clause (today a nonexistent integer matches nothing; dropping the entry would widen the filter to everything, `app/api/me/sessions/route.ts:139,301-313`). The mute DELETE and the unban charge their limiters today before writing (`lib/userMute.ts:66-68`, `bans/[identityId]/route.ts:45-51`), so their null paths charge and 429 like a real target. A MALFORMED `hosts=` entry (an old tab's `u:42`) is also a FALSE clause, not a silently dropped one. The self-target and `d:` checks run on the translated value. Context for weighing this: a logged-out profile GET already tells "exists" from "deleted" for an id the caller holds (no viewer, so no block check; by design, § 11), so equalizing the null paths is defense in depth that matters for the signed-in block cases.
- **Arrays** (`taggedUserIds`): any element that isn't a well-formed public id → 400 for the whole request, so an old tab's integer list can never become `[]` and wipe a post's tags (the PATCH deletes and re-inserts, `app/api/checkins/[id]/route.ts:210-226`). Well-formed unknown ids drop like a non-mutual tag. A length cap before the lookup. Resolved BEFORE the check-in transaction: tags are written after COMMIT, so a late 400 would leave the post created and a retry duplicates it.

**Outbound:**
- 🔒 **`metaToWire` is an allow-list**, used by `buildMetaView` and the three routes that echo meta (join, set-role, settings). Today `buildMetaView` spreads `...meta` (`lib/sessionState.ts:176`), so any future id field would leak by default (the `redactWine` `...rest` lesson). It is a `Record<keyof SessionMeta, …>` like `SESSION_META_PERSISTENCE` (`lib/session.ts:259`), so a new meta field fails tsc until it is classified, plus a key-set test.
- `wineToWire` is synchronous (`lib/session.ts:144`), so the builder and the four wine-echo routes pass in a pre-fetched public-id map (the users read `buildKickedUserNameLookup` already does can carry it).
- Session reads: the builders in `lib/sessionState.ts` (`participants[].id`, `hostUserId`, `hostIdentityId`, `coHostIds`, `providerIds`, `viewerBlocksOut` / `In`, ratings map keys), `wineToWire` / `redactWine` (`addedByUserId`), and the routes outside the builders: create / join / visit `id`, removed-state, the bans list, the ban preview echo, the moment preview's `hostUserId`, the wine echoes (POST, PATCH, reassign, reorder, reveal), `/api/me/sessions` (`people[].id`; it stops spreading `host_user_id`).
- Profile, people and feed rows: about 10 hand-written mappers (`profileLoad`, `profileHeader` faces, `profilePeople`, search, friends, tasted-with, blocks, mutes, feed author + tags, the check-in POST / PATCH echo, the profile's blocked and shell views). Each select adds `public_id` and emits it as `id`; the canary scan (§ 9) keeps them honest.
- **People order (D3, newest follow first):** Followers and Friends by when the person followed the owner (Friends is followers with the mutual filter, so it stays index-served), Following by when the owner followed them; tie-break `public_id`. 🔒 **The cursor is sealed:** AES-GCM over the last row's exact `created_at` (epoch microseconds: the column stores µs and a JS `Date` would truncate to ms and skip the rest of that millisecond) and `public_id`. Its associated data binds it to (viewer, profile, tab, `mutual`, `known`, `q`): unbound, a cursor minted at a known moment on your own list would replay on anyone's list and date their follow edges. The key is derived with HKDF and a purpose label from the secret chain `lib/registerToken.ts:7-10` uses (`AUTH_SECRET || NEXTAUTH_SECRET || JWT_SECRET`), and it THROWS when none is set (an empty key would make cursors forgeable; `lib/betterAuth.ts:24` falls back to `''`, and the synthetic sign-up HMAC throws the same way now). A random 12-byte nonce per seal and a version byte. Every instance agrees, no new env var. The client never sees a time (follow dates are never shown, People plan D2), and the server never looks up an edge the caller names (that would probe follow edges `blockScrub` hides, `docs/dev/block.md`). The keyset is written `f.created_at <= $t AND (f.created_at < $t OR u.public_id < $p)` so the new indexes serve deep pages. A value-based keyset survives an unfollow between pages; a tampered or mismatched cursor answers `{ users: [], nextCursor: null }`. A re-follow moves a person to the top (that's what newest-first means). Measured on the 10M-follow graph per tab, including a profile with about 30k mutuals.
- The `u.id` tie-breaks elsewhere (search `u.name, u.id`, tasted-with, the in-common pick of 12) move to `public_id`.

## 5. Auth surfaces

Clients need their OWN id in the public form (the app builds `u:${session.user.id}` in six places), so `user.id` in everything a client receives becomes the public id. Server-side `auth()` and `resolveUser` keep the integer.

- 🔒 **The rewrite lives only in our two route wrappers**, on parsed JSON after the handler returns, touching exactly `user.id` and `session.userId` (never a text replace: `name` is user-supplied in the same body). Every JSON body is re-serialized UNCONDITIONALLY (always write `id`, always delete `image`), so a real and a synthetic sign-up come back with the same headers; every other header is kept (the heartbeat's Set-Cookie is the device's only record of the extended expiry) and Content-Length goes. Never through a BA hook or `customSession`: server-side `getSessionFromCtx` would see a non-integer id and the change-password `rl:account` charge and the revoke hooks would skip silently (`lib/betterAuth.ts:297-305,332-334`); those hooks throw on a non-integer id instead of skipping.
- **Native** (`app/api/auth/native/[...all]/route.ts`): also drops `user.image` from every body. BA's Redis session copy snapshots the user at sign-in (its `image` is the old `avatars/u_<int>_…` URL) and nothing refreshes it for up to a year; the app never reads it (build check). The public id comes from `publicId` on the user object, else one lookup (copies written before the deploy lack the field).
- **`/list-accounts`** is live and returns the integer twice (`userId`, and `accountId` = the user id for the credential row): it goes into `disabledPaths` and `REQUIRED_DISABLED` (`scripts/check-better-auth-config.mjs`). The app doesn't call it.
- **Sign-up enumeration:** `customSyntheticUser` returns a public-id-shaped HMAC as both `id` and `publicId`, which removes the id-format and sequence tells; the name / image / invalid-name tells go too (§ 8a a). A follow-up sign-in still tells them apart until email verification.
- **Web:** the `session()` callback adds `public_id` to the users select it already runs. One `clientSession(session)` mapper (`user.id` → the public id) is used at EVERY server-to-client hand-off: the root layout's `<SessionProvider>`, `app/me/layout.tsx`, `app/me/page.tsx` (passes the whole `session.user` to `MeDashboard`), `app/me/feed/page.tsx`, `app/u/[id]/page.tsx` (its props carry the parsed integer and the viewer id, and client components build API URLs from them), and the `/me/profile` redirect. The NextAuth route becomes a wrapper that rewrites GET AND POST `/api/auth/session` (`update()` POSTs). The client copy also drops `userSessionId` (no client component reads it). The web register response stops returning `user.id`.

## 8. The S3 keys

Four public-read key shapes embed the integer: `avatars/u_<id>_`, `avatars/cover_u_<id>_`, `avatars/tile_<tile>_u_<id>_`, `wines/ci_<id>_` (check-in photos: the had-a-sip copy, POST, PATCH; an earlier PATCH also wrote `wines/ci_<id>_<checkinId>`).

🔒 **Ruled (D2): an image address carries nothing that points to a person**, neither the integer nor the public id, for new uploads AND existing objects.

- **New keys:** a kind marker and a cryptographic random part (≥ 16 characters), no user, no timestamp: `avatars/avatar_<rand>`, `avatars/cover_<rand>`, `avatars/tile_<tile>_<rand>`, `wines/ci_<rand>`.
- 🔒 **Tile ownership moves from the key to the row: `tile_*_own_url`** (own ⇔ `tile_*_url = tile_*_own_url`), written in the same update as the URL and read in the same `FOR UPDATE` select as the prior value. The user id in today's key prefix is load-bearing: a pin is a REFERENCE that can point at a photo you don't own, and the owner binding is what stops a pin of someone else's public tile URL, followed by a replace, from reclaiming their bytes. A URL match rather than a boolean because the old code still serving during the rolling deploy ignores the new column: an old-instance pin over an own upload would leave a boolean `true` on someone else's photo, while a URL match can only become unequal (at worst an orphan, never someone else's bytes).
  - Readers: the replace reclaim, `writeProfileFields`' prior (a pin write touches only the tiles in the request), `resolveTilePhotos` / `readPins` / `clearDeadPin`, the photos route, account deletion's `FOR UPDATE` select (`lib/accountDelete.ts:320-321,439`).
  - Backfill: `own_url = url` where the url passes today's exact `isOwnTileUpload` test (not a `LIKE`: `_` is a wildcard, `_u_42_` would match `_u_421_`).
  - Until the re-key has run in prod, a legacy own prefix also counts as own (today's rule); then that rule goes. The re-key also sets `own_url = new` whenever the old URL passes the legacy own test for that row's user and tile: an own upload made through an old instance during the overlap has a stale `own_url`, and moving only `url` would make it not-own, so the next profile read would clear it and orphan the object. The dry run counts such rows.
- **Existing objects:** an operator script, `scripts/rekey-user-images.mts`:
  - Discovery: `ListObjectsV2` over the user-bearing prefixes AND every URL column (`users.image_url`, `cover_photo_url`, the three tile and three own-url columns, `wines.image_url`, `rating_images.image_url`). Keys are parsed from the `/<bucket>/` segment, independent of the stored endpoint prefix; rows under a foreign prefix are reported.
  - One object at a time, in ONE shuffled order across all users (CopyObject stamps `Last-Modified` with the copy time, so going owner by owner would group one person's photos by time): copy, then a short transaction that locks the owner's users row `FOR UPDATE` (it serializes with replace, profile PATCH and account deletion) and compare-and-sets every column holding the old URL (`WHERE col = old`). 🔒 Every new key is written to the manifest BEFORE its compare-and-set: the check-in PATCH and DELETE read the prior image outside any users-row lock (`app/api/checkins/[id]/route.ts:269-272,362-366`), so a copy can lose its race after the compare-and-set too.
  - Dry run by default: counts, foreign prefixes, missing sources, overlap-era own tiles.
  - `--reclaim`, a separate later run (repeatable): deletes an old object or a manifest key only when no column references it (a crash between a copy and its compare-and-set leaves the old URL live). Until then already-loaded pages keep their images and the old objects remain the way back. The manifest and the per-object log pair integer-bearing old keys with new ones: they stay operator-local and are deleted after the reclaim.
  - A runbook entry in `docs/dev/deployment.md`, with the S3 variables the runner needs, and a check that anonymous `ListObjects` on the bucket is denied (D2 rests on it; the local policy grants only `s3:GetObject`, `README.md:123`).
- Moment covers made by the settings path are random; the CREATE path still names them `sessions/new_<ts>_<Math.random 8 chars>` (about 41 bits, not cryptographic): fixed in § 8a.
