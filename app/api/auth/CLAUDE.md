# app/api/auth/ — Auth routes

Local rules for `app/api/auth/*`. Root CLAUDE.md still applies; this is overlay context for register/login flows.

## Bot defenses on `/api/auth/register`

- **Honeypot field**: an offscreen `<input name="website">` rendered by the register form. Real users never see it; bots scraping the DOM tend to fill plausibly-named text inputs. Non-empty submissions reject with a generic 400.
- **Signed-timestamp form token**: `lib/registerToken.ts` mints a `<timestamp>.<hmac>` token at page render (server component, `force-dynamic`). The form posts it back with the body. Server verifies the HMAC, accepts only `>= 800ms` and `<= 30min` old. Rejects forged signatures, too-fast submits, and stale tokens with the same generic 400.
- Both checks run **before** the bcrypt hash + DB write, so a tripped honeypot or bad token costs the server effectively nothing.

HMAC secret is pulled from `AUTH_SECRET` (falls back to `NEXTAUTH_SECRET` / `JWT_SECRET` for compatibility). See `lib/registerToken.ts`.

## Login precheck

`/api/auth/login-precheck` exists to surface rate-limit errors that NextAuth v5 strips from `signIn()`. Uses `peekRate` (no increment); only the actual `authorize()` call increments on bcrypt failure. See `app/api/CLAUDE.md` for the broader rate-limit pattern.

## Trust anchor mechanisms

Trust-anchor principle (identity-ids only, display names presentation-only): see root CLAUDE.md "Trust model". Resolver API (`resolveIdentity`, `participantOrBanned`): see `lib/CLAUDE.md`.

This file documents the **mechanisms** that produce each trust anchor on `app/api/auth/*` routes:

- **Logged-in users** carry a NextAuth session cookie (`__Secure-authjs.session-token`, JWE-encrypted, 30 day lifetime). Resolved server-side via `auth()`. The cookie's JWT carries an opaque `userSessionId`; the `auth.ts` `jwt()` callback gates **every** authenticated request on `user_sessions.revokedAt` (this replaced the never-written `users.tokenVersion`). A token with no `userSessionId` (pre-feature/"legacy") is treated as invalid → forced re-login. **Never cache `auth()`** — any cache TTL is a revocation gap (see `lib/CLAUDE.md`). Per-device sign-out / password-change-revoke / logout-revoke all set `revokedAt` (+ a `revocationReason` that drives the tailored login-page notice via `lib/revocationNotice.ts`). Full design: `docs/dev/proposals/auth-sessions.md`; cross-cutting invariants: `lib/CLAUDE.md`.
- **Anonymous users** carry a per-session anon token (`crypto.randomUUID()`, stored in browser `localStorage` as `vr_anon_<CODE>`). Sent on every request as the `x-vr-anon-token` header. Maps to `s:{CODE}:tokens` → identity id. (Anon flow never touches `user_sessions` — the two trust models stay disjoint.)
- **Native (mobile) users** carry a Better Auth session cookie (signed opaque token, validated against the dual `auth_sessions`/Redis store on **every** request — `cookieCache` off, CI-pinned). Resolved server-side via `lib/resolveUser.ts`, the single seam every API handler uses: BA branch first, fall through to `auth()`; both branches return the same NextAuth `Session` shape, so downstream code is blind to which credential authenticated. Claims are never merged across branches. Revocation goes through `lib/identityStore.ts` (never raw `auth_sessions` row deletes — root CLAUDE.md "Redis-first"). Mounted at `/api/auth/native/[...all]`; full design: `docs/dev/proposals/mobile-app/01-identity-and-auth.md` §5a. **Lifetime**: 1-year sliding inactivity window (`session.expiresIn`/`updateAge` in `lib/betterAuth.ts`). 🔒 Only the HTTP get-session heartbeat slides — `resolveUser` passes `disableRefresh`, because a server-side slide never reaches the device's stored cookie (comment there). Expired rows are retired daily in-process through the chokepoint (`pruneExpiredNativeSessions`, scheduled by `lib/nativeSessionPrune.ts` — never raw SQL); pinned by `scripts/tests/ba-session-lifetime.mjs`. Native "last seen" (`auth_sessions.updatedAt`) moves once per 5-minute bucket, the grain of web `user_sessions.lastSeenAt`: `resolveUser` bumps it through Better Auth's `updateSession` (`updatedAt` only; rationale in `lib/resolveUser.ts`, pinned in § 10 of the suite). Other consequences: a replaced phone stays in Connected devices until its window lapses unless revoked; the native revokes (`/revoke-sessions`, `/revoke-other-sessions`, `/change-password`) do NOT use BA's list-driven implementations — the before-hook answers the first two from a Postgres snapshot (`revokeNativeSessionsExcept`), and the `account.update.after` hook does the same for a password change (caller keeps its current session, like web; failures leave PG rows as retry targets). A refresh racing a completed revoke can write a Redis copy back with no row behind it; `secondaryStorage.get` treats a copy without a row as unauthenticated and deletes it, so the race can't resurrect a session. **Connected devices for an app caller**: `resolveUser` carries the caller's own `auth_sessions` row id as the server-only `nativeSessionId` (never the token), so the devices GET flags This Device, the per-id DELETE treats the caller's own `ba:<id>` like the web's own current row (no password; the app signs out through `authClient.signOut()` instead), and revoke-all accepts an app caller (`revokeAllForNativeCaller` keep-by-id: every web and every other native session). **Device label**: the app sends `Verre/<version> (<model>; iOS <version>)`; `parseNativeUserAgent` (only in the BA `session.create.before` hook, so a web login can't claim it) stores "<model> · Verre App", else `parseUserAgent` as before. Labels are written at sign-in only (the create-only invariant in `lib/betterAuth.ts`): an older "Unknown device" row keeps it until that phone signs in again. **Email change from the app** (`PATCH /api/me/account` `{ email, currentPassword }`): a native caller (`authSource === 'native'`) must re-confirm the current password (checked against `users.password_hash`, charged to `rl:account`), and the address must pass `z.email()`, Better Auth's own sign-in check, or the app would lock itself out at the next sign-in; the web form sends no password and is unchanged (ruled 2026-11-11). No confirmation mail (no email pipeline); Better Auth signs in by `users.email`, so the new address works at once and the old one stops.
