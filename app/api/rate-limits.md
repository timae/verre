**Per-endpoint rationale:**

- **Login**: brute-force on stolen email knowledge. Counters increment on bcrypt failure only — successful logins don't pollute.
- **Register**: mass-signup spam. IP-based; combined with bot defenses (honeypot, signed-token) gating before the bcrypt + DB write.
- **Account PATCH+DELETE**: brute-force the password re-auth check from a stolen session cookie. Shared so an attacker doesn't get 20+20.
- **Avatar POST**: storage abuse via a stolen session cookie. DELETE is currently uncapped (`app/api/me/avatar/route.ts` has no `checkRate` call on DELETE) — flag for review if abuse appears, but DELETE is idempotent and reclaims S3 rather than consuming it.
- **Profile cover POST**: storage abuse from a stolen cookie, like the avatar POST; its own counter so cover and photo uploads don't starve each other. DELETE is uncapped (it reclaims S3).
- **Tile photo POST** (your own photo on a profile tile): the same storage abuse, three tiles behind one counter (20/h, about the cover's 10/h per two tiles); its own key so tiles, cover and photo don't starve each other. Taking one off (the profile PATCH: another pin or `null`) reclaims and rides the profile-edit budget.
- **Profile PATCH** (name, bio, tile covers): content churn from a stolen cookie (a rename fans out to every live session the user is in). Deliberately NOT the account PATCH, which charges the shared password-guess budget `rl:account` 20/h on every call, a plain rename included; editing your bio must not eat the budget that guards your password.
- **Username GET / PUT / availability** (`docs/dev/proposals/usernames.md` § 8): the GET is read-side noise (three small queries). The PUT's real bound is the rename QUOTA (5 counted changes per rolling 90 days, in Postgres, `lib/username.ts`); `rl:username-set` only bounds a stolen cookie hammering the write path with names that are taken (each attempt is a transaction that locks the user's row). Charged after validation, and not for the same name again, so a form that re-submits or a typo costs nothing. The availability check tells whether a username exists (taken and held answer alike), by design; per user 60/min for someone typing, plus a per-address backstop because free accounts multiply a per-user budget (`checkRates` charges both; both after the 401, the address from `getClientIp`). It is advisory: the PUT's answer from the database is the authority.
- **Profile photos GET** (the tile picker): read-side noise; each call runs the per-tile pool query.
- **Visibility GET / PATCH (outer)**: read-side noise + general burst protection. Distinct counters per HTTP method.
- **Visibility PATCH (inner)**: stolen-cookie thrashing the audit log + flipping visibility. Enforced inside `setProfileVisibility` via peek-then-`checkRate`-on-change: an actual change of ANY of the six settings counts once per PATCH; a no-op (or an already-applied retry) and a 409 compare-and-set refusal charge nothing.
- **Sessions GET (`q`/`people`)**: charged ONLY when the caller sends the two genuinely-expensive params — the `pg_trgm` `word_similarity` search (`q`) or the per-friend correlated `EXISTS` (`people`). The OTHER filter params (`tense`/`roles`/`hosts`/`category`/date/`cursor`/`limit`) are plain indexed WHEREs + keyset paging, no costlier than the unfiltered carousel read — and since the client ALWAYS sends `tense` for Recent/Upcoming, charging on "any filter param" would throttle ordinary browsing (open list → scroll → each page a request) against a search-compute cap. So the gate is `q`/`people`, not "filtered". Capped like `/api/users/search`; blast radius smaller (every query is `sm.user_id = me`-scoped, only the caller's own sessions), so 30/min is generous. The unfiltered carousel read (home hot path, every focus) stays uncapped.
- **People lists** (`/api/users/:id/followers` + `/following`): enumerating someone's social graph, and each page now runs the per-row lines (moments together, friends in common) and the photo gate. Per USER (60/min), so one shared NAT address isn't one budget, PLUS a per-IP backstop (300/min) because per-user alone multiplies with accounts per address; `checkRates` charges both even when one refuses. Both AFTER the 401, so anonymous traffic can't burn a shared address's budget; the IP from `getClientIp` (single-entry XFF only), never a raw `x-forwarded-for[0]`. Measured on a seeded 10M-follow graph: ≤ 20 ms warm for a viewer following ~30k.
- **Profile lists** (`/api/users/:id/impressions`, `/moments`, `/cravings`, lists plan D11): one budget for the three, like the people lists: per USER (60/min) plus a per-IP backstop (300/min, accounts per address would otherwise multiply it), both after the 401, the IP from `getClientIp`. Each page is a caller-scoped query over one person's rows (ILIKE + trigram search included, so search rides the same budget). Someone's Moments with `q` or `people` ALSO charges `rl:moments-search` (the same key string as `/api/me/sessions`), so your own and someone's moment searches share the 30/min search budget. `/api/feed` (its `?item=` included) stays unlimited, as before: `item` is one more condition on the same gated query.
- **Profile GET** (`/api/users/:id`, and by username: `/api/users/by-username/:username`): public and anonymous-readable, so IP-keyed (`getClientIp`) against enumeration and DB-load amplification. Both API routes and both web pages (`/u/<id>`, `/@<name>`) charge the SAME key string, so a lookup by name buys no second budget, and the pages read the address through `getClientIp` too (the `/u/<id>` page used a raw `x-forwarded-for[0]` before). 🔒 The target is resolved AFTER the charge: a spent budget runs no lookup. Names can be guessed where random ids could not: logged out, `/@<a common name>` shows the display name of a non-public account at this rate (accepted by ruling, usernames § 15). Note for the app: each relationship write fetches its target's header, and the trailing refresh refetches the mounted headers, so a burst of follows from one address draws on this budget (`apps/mobile/src/lib/relationship.ts`).
- **The impression read** (`/api/users/:id/impressions/:ratingId`, Moment Visibility step 3): one row of the Impressions list for its page, so it rides the lists' own budget (the same key strings, charged once per read, after the 401, before the owner is resolved).
- **Post privacy** (`rl:post-privacy`, step 3): your own choices in a moment (Incognito and Hide from Feed on the Moment Privacy page, Incognito in the web guest menu) and your post's ⋯ row (Hide from Feed). A stolen cookie toggling a person's visibility back and forth; ONE key string for both routes, so the two can't stack 30 + 30. 🔒 **Hiding is never charged or refused** (ruled 2026-11-24, R10: a protective path, like Unblock): only SHOWING again counts, and only when it is a change (the route reads the current choice first; already shown is answered with nothing written or charged; a slot is RESERVED before the write and given back when the write changed nothing (a twin got there first) or failed, and on a refusal, so two at once cost one and a burst can't overshoot; a refused show whose choice is already shown is answered, not refused: Codex 2026-11-25), so a back-and-forth stays bounded by its show half, and one guest hammering a venue's shared budget can't stop the others from hiding their names. A guest is keyed on the moment and the ADDRESS (`getClientIp`): an `a:` identity is re-minted on every join (the catalog-link reasoning), and one address is one venue (the join cap's reasoning), so 120 an hour per moment leaves a venue room.
- **Moment Defaults** (`/api/me/moment-defaults`, `docs/dev/proposals/moment-defaults.md`): the GET is read-side noise (one primary-key read). The PATCH bounds a stolen cookie churning your defaults (each save also runs one count of what differs); a no-op save is free, and 🔒 a change that makes a default MORE private is never charged or refused (R10), so the alert's Cancel, which undoes a widening by saving the old value back, always lands (Codex build r9: on a spent budget the undo was refused and the less private default stayed). **The apply** (`/apply`, the "All N …" of the app's alert) changes many moments or posts at once, so it follows R10 (hiding is never charged or refused, like Unblock) with its own small budget (D6, ruled 2026-11-25): a WIDENING action (a Visible To that opens, a host switch going on, an Incognito / Hide from Feed show) RESERVES one slot on its section's key (`rl:moment-defaults-apply:<host|moments|checkins>`, 10/h) AND one change on the single-item key a per-moment write of it would charge (`rl:moment-visibility` for host fields, `rl:post-privacy` for your choices and check-ins), so a bulk show can neither bypass that bound (one action, one change) nor be always refused by it (200 moments, one change). 🔒 A refusal on EITHER key refunds BOTH (`checkRate` increments before it compares; otherwise ten refused bulk attempts would starve the single-item show), and the pair is settled by COMMITTED widenings: none (nothing changed, only narrowing, a throw before any widening) → both refunded; one or more → both stay. The reservation is never taken while a Postgres lock is held (host moments are visited in two passes: every narrowing first, then the reservation, then the collected widenings under their locks again). A refused widening answers 429 after the narrowing part applied. The request limiter (`rl:moment-defaults-apply-req`, 60/min) bounds repeated scans: peeked first; spent and the default can only widen → 429 before the scan; spent otherwise → only the narrowing part; charged only when the apply changed nothing (a hide loop still pays its scan each time: named). 🔒 Every Redis call of the apply has a 500 ms deadline (the shared client queues commands while disconnected): the request limiter fails OPEN on a timeout (a hide must reach Postgres), the widening reservation fails CLOSED: it is granted only when Redis CONFIRMS both charges (a timeout or a Redis error is a refusal: `checkRateOrThrow`, Codex build r1: plain `checkRate` allows on an error, so a failover to a read-only replica would have widened uncharged), and a refusal refunds only the keys that were charged (an answered one at once, a timed-out one only once its increment confirms, never an errored one: Codex build r2); a 429's wait is the refused counter's own (60 s for a timeout or an error). Residuals (named, plan § 8): a refund that lands after its window rolled over erases one charge of the next window (step 3's accepted edge); two host applies at once can each be charged.
- **Search** (`/api/users/search`): unchanged 30/min/user; the block filter now runs in SQL before the limit of ten. It matches the username as well as the name (two trigram indexes, a BitmapOr from 3 characters; a 2-character query scans, as the name search always did).
- **Tasted-with** (`/api/me/tasted-with`, Add Friends' "People you tasted with"): read-side noise from a stolen cookie; one grouped query over the caller's own moment memberships per call.
- **Mutes GET**: read-side noise from a stolen cookie polling the list; one indexed query per call.
- **Mutes POST+DELETE**: stolen cookie thrashing the table or generating noise. Shared.
- **Blocks POST**: stolen-cookie burst-blocking. DELETE intentionally **uncapped** — recovery path from a burst-block attack must always stay open.
- **Checkins POST+PATCH**: content/storage spam from a stolen cookie (each POST can mint a wine row + S3 image; PATCH can replace images). Shared counter so creates + edits can't stack to 100+100; since 2026-07-17 the same PATCH counter also covers session-rating edit bodies (`kind='session'` feed items). Since the catalogue model change (step 3) the photo is not part of the create: it attaches with a PATCH carrying only `imageData` (ruled 2026-11-20: that first photo costs no second slot). Exempt only when the check-in is the caller's own, has no photo yet and was posted in the last 10 minutes; a photo with any other field, a second photo, a removal, or someone else's id is charged, so a remove-and-re-add loop still pays one slot per round, and every probe still pays before its 404. DELETE is uncapped like avatar DELETE — idempotent, reclaims S3 rather than consuming it.
- **Saves** (`rl:crave`, ruled 2026-11-20: a generous backstop): a stolen cookie hammering saves and unsaves. One budget for the moment's and the post's toggle, charged after the moment's entrance and participant gates, or after the post gate and the check that the bottle is the post's, so a probe of a moment or post the caller may not see costs nothing. A save is idempotent and a save of a hidden bottle stores the same row whatever the wine, so the limit guards load, not an oracle. Removal by key (`DELETE /api/me/bookmarks/:key`) stays uncapped, like the other removals.
- **Catalog search**: a `pg_trgm` scan across the whole catalog is the expensive query in the wine-catalog feature, so it is capped like `/api/users/search`. Since step 7b the app's one field (`kind=bottle`) and the every-word producer search ride the SAME key: two statements over Verre's own search docs (four when nothing fits or fewer than 5 wines do, five with close matches), measured 3 to 21 ms end to end on the full catalogue (dev DB, from the sandbox, warm, 2026-11-21; after the 2026-11-22 changes (short lists widened by the typo pass, typo lookups on the first letter, the words statement kept below the JIT threshold) a two-word search about 8 ms p50 and 13 ms p95, a query of eight unknown words about 11 ms; a query of nothing but unknown words about 50 ms, three typo lookups). On a 1/8-core app a search whose words match more than 400 wines costs about 9 ms of app CPU against about 4 for a selective one (sandbox container, 2026-11-21): the budget, not the database, is what bounds it. The app sends one per pause in typing, so a bottle picked through the one field costs about as many calls as before (the app sim counted 3 searches + the year lookup for one bottle typed in three pauses; the old producer-first flow measured about 6 in step 1); no budget change (a change would be a ruling). Caller-keyed rather than IP-keyed — IP would bucket a shared-NAT office into one budget. The global route needs a signed-in caller; a signed-in caller of the moment's search (`/api/session/:code/catalog/search`) charges the SAME key, so the two don't stack. **A guest** (who may pick an entry but not create one, and needs a search to pick) searches only inside a moment they may add bottles to, behind the entrance gate, and is keyed on the IP (`getClientIp`): a guest identity is re-minted on every join, the `catalogLinkRateKey` reasoning. 60 a minute to start (one venue's guests share an address, but only hosts and bringers search; step 1 measured a search flow at about 6 calls); accepted by ruling: anyone who creates a guest moment can search the catalogue at that rate (it is open; this widens who may search it, at a bounded rate). The two halves stack for one person: signed in, 30 a minute as a user, plus 60 a minute per address as the guest host of a guest moment of their own (named, accepted with the ruling). The picker sends about six calls per bottle (step 1 measured that flow: three producer searches while the name is typed, two product searches, one vintage lookup), so 30 a minute is about five bottles a minute for one person.
- **Catalog entries POST**: catalog rows are permanent identity (one ID for life, never re-minted) and a junk entry can only be cleaned up by a curator, so creation is capped harder than search — the blast radius of spam here is a polluted shared catalog, not just wasted compute. 60/h is generous for a human adding wines during a tasting while bounding a stolen cookie. The same key bounds the `create` of every bottle write (catalogue model change step 4: a new wine is minted in the bottle's own transaction), so adding through a moment and through the catalogue endpoint can't stack N+N. The limiter sits *behind* the kill switch (`CATALOG_PUBLIC_ENABLED=false`, see `docs/dev/deployment.md`), so while it is on only staff can consume it.
- **Catalog link on session wines** (`rl:catalog-link`): the wine POST/PATCH routes accept `productId`/`vintageId` and validate them against real catalog rows, which makes them a catalog-existence probe reachable from **outside** the `CATALOG_PUBLIC_ENABLED` fence — any wine-adder qualifies, including the anonymous host of a session they created themselves. Previously these two routes had no limiter at all, so this was the cheapest way to probe the catalog (an indexed PK lookup, versus the deliberately-capped trigram scan on `/api/catalog/search`). 🔒 **Keyed on the USER when logged in, but on the IP when anonymous** — and the anonymous half is the load-bearing one. An `a:<uuid>` identity is minted fresh on every join (a successful join charges nothing; guest joins are capped at 60 per address per moment per 10 minutes), so a caller holding one valid code (trivially, one they created) can rejoin in a loop and collect many identities. Measured: 20 rotated identities bought 20× the budget against a per-identity key. `catalogLinkRateKey` in `lib/catalogWrite.ts` is the single spelling of this. **Charged when a link is PICKED** (a `create` charges `rl:catalog-create` instead; a cosmetic edit charges nothing). ⚠️ Since the catalogue model change (step 4) every new bottle links, so this is now ALSO the cap on adding bottles by pick: 120 an hour per signed-in user, and per ADDRESS for guests (the guest hosts of one venue share it; a tasting adds a few dozen at most). Shared key across POST and PATCH so add + edit can't stack 120+120. The reason this is a limit rather than a gate: linking to an already-existing catalog entry is a read-only reference, not catalog authorship — the kill switch (`CATALOG_PUBLIC_ENABLED=false`) stops *creation*, never a pick. Defence in depth: `resolveCatalogLink` returns ONE generic message for every denial, so a probe learns nothing about which ids exist.
- **Session POST**: code-space exhaustion (8-char Crockford, but mass enumeration would crowd legitimate creates). The create-time cover upload rides this same 10/10min counter (one create = at most one cover), so it needs no separate limit.
- **Settings PATCH cover** (`rl:cover`): storage abuse from a stolen host cookie thrashing cover replaces. Mirrors the avatar POST limit; charged only when a data URL is present so no-op settings saves don't burn slots. Removal (`coverPhoto: null`) is uncharged — like avatar DELETE, it reclaims S3 rather than consuming it.
- **Moment Visibility read** (`GET /api/session/:code/visibility`, dark behind `MOMENT_LOOKIN_ENABLED`): read-side noise; each call is one read of the moment's row by its code (the unique index). Charged after the entrance gate and the flag (a flag-off 404 charges nothing). Per USER when signed in; per ADDRESS (`getClientIp`) for a guest, whose `a:` identity is re-minted on every join (the catalog-link reasoning above), so a per-identity key would be rotatable.
- **The look-in** (`GET /api/moments/:publicId`, dark behind `MOMENT_LOOKIN_ENABLED`): the app polls a look-in every 5 s like the moment screen (12 a minute), so 60 per user leaves room for moving between moments; 600 per address is 50 lookers behind one address. The same budget covers the details reads (`?bottles=`, the open Compare cards' aromas): the app sends at most one every 2 s with at most 10 keys, and its first reads and details reads go through one fetch gate per look-in with no retries, so one open look-in costs at most 42 a minute (12 + 30) whatever is opened (`apps/mobile/src/lib/lookInDetails.ts`, step-2 plan T4). Charged on EVERY request after the 401 and BEFORE the id is parsed or anything is looked up, so a refused request costs the same for every id. No guess budget: a public id has about 60 random bits and a link token 128; the limiter bounds cost. One look-in of a 200-taster, 30-bottle moment is eleven statements, about 33 ms in the sandbox; a details read of 10 bottles about 15 ms (measured: `.local/moment-visibility/step2-plan.md` § 9).
- **By-moment** (`GET /api/me/sessions/by-moment/:publicId`): the only route of the feature that answers a code, and only to the moment's own members (the record's rule); anyone else gets the look-in's 404. Per user plus a per-address backstop (free accounts multiply a per-user budget), both after the 401.
- **Moment Visibility writes** (the visibility PATCH and `POST /api/session/:code/look-in-link`): a stolen host or cohost session thrashing who can look in, or resetting the link over and over (each reset kills the link people hold). ONE key string for both, so a save and a link action can't stack 30 + 30. Signed-in only (a guest is refused before the limiter: it has no account to key on and no power to write), charged on every request that passes the gate and the flag, a no-op included: 30 an hour is far above someone setting up a moment (four settings and a link).
- **Wrong moment codes** (`rl:code-miss`, leak-fixes F2): every moment route answers "no such moment" (404) differently from "not yours" (401 / 403), and the join POST, the join page and the preview must say "no moment for that code" by design, so each is a code oracle. A WRONG code costs budget, a right code costs nothing, and the budget is never reset (a reset on a valid code made one valid code, your own moment, buy unlimited guesses). Charged once per caller and code per hour (a seen marker: a deleted moment's open screen, the web's 404 → `/join` bounce, cost one charge, not one per poll, and still read "gone" on a spent budget), as a RESERVATION taken in ONE atomic Lua step before the moment is opened and refunded for a right code (`reserveMiss` / `settleMiss`, `lib/rateLimit.ts`): a parallel burst gets no more requests past the entrance than the budget has room for (a read first and a charge after the open let every request of a burst read "not spent"), and a spent counter refuses before anything is incremented, so a spent account never pushes the address counter. 🔒 **The entrance gate** (`openSessionFor`, `lib/sessionRoute.ts`): once a caller's budget is spent, only the moment's members get past the entrance (the record's member / rating author / strict host, or the cache's roster / meta-proven host / kicked marker; kicked and banned former members count, their "removed" answer needs it); everyone else gets the same 429 at once, before any route limiter, promotion, contract or rebuild runs, so the answer can't tell a right code from a wrong one. A check placed after a route's own decision re-created the oracle through that decision (401 vs 429, a 503 "restoring", `/visit` registering a stranger). Per account 60/h; per ADDRESS split by code length: 3,000/h for 8-character codes (a big event's shared Wi-Fi mistypes them) and 300/h for the old 4-character ones (65,536 hex codes; at 300/h one address needs about 9 days to sweep them all, named residual R5: they stay joinable, ruled). Residuals: a right code still shows the moment's name and host on the join page (an invite, R1); free accounts multiply the per-account budget (the per-address one bounds that, R2); someone who spends an address's budget also stops strangers' right codes from that address for up to an hour (R7, members unaffected), and on a spent budget a GUEST member of a moment whose cache was evicted is refused too (the spent path never rebuilds: a rebuild would be the timing tell; signed-in members are admitted by the record); the gate fails open on a Redis error, like every limiter here; a code a caller paid for (seen absent) can be re-polled free for that hour, so they can watch it for creation (negligible for 8-character codes; only new 8-character codes are minted); a request in flight across its counter's expiry refunds into the next window (at most one charge erased per such request), and a process killed between the reservation and its settle leaves the charge in place (fails closed, for the hour).
- **Session join POST**: failed attempts (a malformed body, a bad name, a ban) charge `rl:join:ip` 30/min/IP, never reset; a success and a wrong code charge nothing here (a wrong code pays `rl:code-miss`), so a venue full of people joining one moment is never throttled. Guest joins (each mints a new guest; a logged-in rejoin is idempotent) are capped per address per moment (`rl:join:anon:<code>:ip`, 60/10 min, reserved before the join and refunded when it doesn't go through), sized for a venue's Wi-Fi: a venue with more than 60 WEB guests on one network joining one moment within 10 minutes sees "Too many guests joined from here." (signed-in and app users never do). No moment-wide cap: one person could spend it and lock every real guest out (R8: a code holder with many addresses can still flood a roster; the host's kick / ban is the remedy).
- **Moment preview GET** (the app's scan result): also a code-validity answer, so code-guessing. Its own budgets are charged on EVERY lookup, right or wrong code, and never reset (review 2026-11-12: unlike a join a preview leaves no trace in the moment): per user (60/h is far above anyone scanning codes) plus a per-IP backstop, since free accounts multiply per address; both charged after the 401 and BEFORE the entrance gate (they answer the same for every code, so they can sit in front of it), which then charges a wrong code the shared `rl:code-miss` budget: the preview and the join can't stack N+N.
- **Places** (`/api/places`, the web check-in modal's location picker, signed in only since leak-fixes F1): every lookup can bill the Google key, and an autocomplete fans out to up to 7 billed calls (1 autocomplete + 6 place details). Per account (30/min, 300/day) plus per address (120/min, 1,000/day, `getClientIp`), charged on every request after the 401; free accounts multiply the per-account caps, the per-address ones don't. Then an app-wide 2,000 requests a day on the Google path only (about 14,000 billed calls), charged only after the per-caller limits AND the input checks pass, and Nominatim's usage policy of 1 request a second for the whole application in front of the OSM search: past either the picker gets `[]` (the user types the venue by hand), never a 429; a Nominatim lookup first WAITS up to about 1.2 s for the next free second (the picker sends one per pause in typing). Residual: two addresses with a handful of free accounts can drain the app-wide Google cap for the day (every picker then gets `[]`): it degrades and leaks nothing; the console quota is the real bound. The real backstop is the Google console's daily quota (`docs/dev/deployment.md` § GOOGLE_PLACES_API_KEY). Named follow-up: fetch place details only on selection, with Google session tokens (about 7× fewer billed calls).
- **Bans POST+DELETE (kick/ban + unban)**: bounded moderation in both directions. DELETE shares the budget (unlike block DELETE, which is uncapped) — moderation actions are not a recovery path.
- **Devices GET**: read-side noise from a stolen cookie polling the list.
- **Devices :id DELETE**: per-id revoke is "one user clicking through their list." 30/h is ample for normal use; the cap bounds a stolen cookie thrashing revokes. **The cross-device password re-auth additionally consumes the shared `rl:account` counter** — otherwise this endpoint would be a fresh 30/h brute-force surface against the same password hash, defeating the whole reason `rl:account` is shared. Own-current-session revoke skips both the password and the `rl:account` charge (it's just a logout): the web caller's own uuid row, or the APP caller's own `ba:<int>` row (`nativeSessionId` from `resolveUser`, the same as Better Auth's password-free `/sign-out`). Every other `ba:` target takes the password path.
- **Devices DELETE (revoke-all)**: separate, lower counter (10/h) because this is a single panic-event ("sign out everywhere"), not list-clicking. Distinct from per-id so an incident-response revoke-all isn't starved by prior per-id clicks, and vice versa. **Its password check also draws from the shared `rl:account` counter** for the same brute-force reason. An app caller is accepted too (keeps its own `ba:` row, signs out every web and every other native session). It has Better Auth's password-free `/revoke-other-sessions` as well, but that one reaches native sessions only; signing out the WEB sessions from a stolen phone is the cross-store, lock-the-owner-out action the password gate exists for, so the app's "Sign Out of All Other Devices" uses this route. Net: account PATCH/DELETE + both device password gates share one 20/h budget against the password hash; the device-specific 30/h and 10/h caps independently bound revoke-thrashing.
- **Better Auth (`/api/auth/native/*`)** — TWO layers (step-7 hardening, proposal §8):
  - **BA's built-in limiter** (`rateLimit` in `lib/betterAuth.ts`), Redis via `secondaryStorage` (`<ip>|<path>` keys, plain integer counters). Belt. Since 1.7 it is one atomic step (`secondaryStorage.increment`: INCR, TTL set on the first hit, so a fixed window) and a request with no resolvable IP shares a `no-trusted-ip|<path>` bucket instead of skipping. 1.6 was non-atomic and failed OPEN on a missing IP, which is why the floor below exists; it is still not relied on as the floor, since its keying and internals are BA's and can move on any upgrade.
  - **Verre's atomic floor** (the braces): a before-hook in `lib/betterAuth.ts` runs `lib/rateLimit.ts` `checkRate` (atomic Lua INCR+EXPIRE) on the auth-critical paths — `rl:ba-signin:ip:<ip>:1m` (10/min), `rl:ba-signup:ip:<ip>:1m` (10/min), `rl:ba-chgpw:ip:<ip>:1h` (20/h). A missing IP buckets into a shared `unknown` key (`getClientIp`), so the cap **fails CLOSED** instead of skipping; the atomic counter holds under concurrency. Pinned in `_ba-e2e-signup.ts` §10. BA's limiter runs first (router `onRequest`, ahead of every hook, on 1.6 and 1.7 alike), so at equal budgets the 429 a client sees is usually BA's generic one (`X-Retry-After`), not the floor's: the floor bounds the attempts, it doesn't shape the response.
  - **IP keying is trustworthy** on Deplo.io: its proxy overwrites `X-Forwarded-For` with the real client IP (`getClientIp` reads it; multi-entry XFF is treated as untrusted). The trusted-proxy invariant is documented in `docs/dev/deployment.md` — it holds only while no untrusted proxy sits in front of Deplo.io.
  - **Sign-up answers honestly; these limits ARE the bound on probing** (usernames, `docs/dev/proposals/usernames.md` § 9; ruled 2026-11-13). The earlier fake success for a taken email (`autoSignIn: false` + a synthetic user) is removed: the app's own follow-up sign-in told a taken email anyway, and the web register always answered 409. `/sign-up/email` now answers 422 `EMAIL_TAKEN` / `USERNAME_TAKEN` / `EMAIL_AND_USERNAME_TAKEN` (and creates the session in the same call), the web register 409 with `fields`. So one address can test at most 10 emails or usernames a minute through the app's sign-up (`rl:ba-signup`, the atomic floor: fails closed on a missing IP) and 100 a minute through the web register (`rl:register`, behind the honeypot and the signed form token), and a signed-in caller 60 usernames a minute through the availability check (`rl:username-check`). Named, not hidden: both tell whether an email has an account. Revisit only with the email pipeline (a generic "check your inbox" is a real answer then).
  - **Native get-session** (live since iOS milestone 1 — removed from `disabledPaths` because @better-auth/expo's `useSession`/sliding-refresh fetch it over HTTP): the app's session heartbeat, hit on every launch/foreground. No Verre atomic floor — it's a cheap read (the Redis session copy, plus one primary-key read of `users.username` in the route wrapper since usernames: Better Auth's copy is a sign-in-time snapshot) with no bcrypt/oracle surface, and the auth-critical paths (sign-in/up/change-password) keep theirs. BA's belt limiter is the only cap; add a floor if abuse appears.
  - **Residual (deferred, named)**: native sign-up has no honeypot/signed-token (web-form-specific — don't apply to a JSON API). The real native equivalent is **App Attest / Play Integrity**, a release-fence item for the app-build phase (`@expo/app-integrity`), rolled out monitor→warn→enforce. Email-verification gating (the strongest anti-spam lever) is blocked on the (separate, deferred) email pipeline. Social sign-up (Google/Apple) is inherently bot-resistant and needs none of this.
- **Native last-seen bump** (`rl:native-lastseen`): not a request limit. `resolveUser` bumps an app session's `updatedAt` once per 5-minute bucket through Better Auth's `updateSession`, which also reads and rewrites the user's whole `active-sessions-<uid>` list, so its cost grows with the user's native session count, and that count is uncapped (sign-in is limited per IP only). Without a budget, one account with thousands of sessions could turn plain GETs (even 429'd ones: the bump runs inside `resolveUser`, before any route limiter) into list rewrites. 30 per user per 5 min is far above any real household of devices; over it, the row simply keeps its last bucket.
- **Native change-password**: brute-forces the CURRENT password from a stolen native session (a re-auth surface, like account PATCH). Charged on TWO counters: the IP floor (`rl:ba-chgpw:ip:<ip>:1h`, 20/h — bounds spray from one IP) AND the per-user budget (`rl:account:user:<id>:1h`, 20/h — the SAME key the web account PATCH/DELETE + `verifyPassword` use, resolved from the session cookie via `getSessionFromCtx` in the `lib/betterAuth.ts` before-hook). The per-user key is the load-bearing one: without it an attacker with one stolen native cookie could ROTATE IPs to bypass the IP cap and brute-force the current password. Sharing the web `rl:account` key means web+native can't stack N+N against the same password hash. (PR#39 review fix — supersedes the earlier "deferred to the step-7 gate, keyed on IP only" note.)
