# lib/ — Server primitives and helpers

Local rules for `lib/*`. Root CLAUDE.md still applies; this is overlay context for shared server-side helpers.

## Redis key namespace

- `s:{CODE}:meta` — JSON session metadata (host, name, blind, blindForEveryone, lifespan, hostIdentityId, hostUserId, coHostIds, providerIds, …). `blindForEveryone` stacks on `blind`: when true, the host/cohost/provider/wine-adder bypasses in `redactWine` (`lib/wineRedaction.ts`) are disabled and only `revealed` un-redacts. Mirrored to Postgres `sessions.blindForEveryone` so every read path outside a moment (the one SQL rule, `lib/outsideView.ts`) applies the same gate without Redis. Disabling `blind` in the settings PATCH cascades to clear `blindForEveryone`.
- `s:{CODE}:wines` — JSON array of wines for this session. For a Postgres-backed moment a PROJECTION of the record (catalogue model change § 8a), still in the old `WineMeta` shape (no colour / sparkling / abv / origin: the previous release and the raw readers parse it)
- `s:{CODE}:wrev` — the line-up revision the cached `wines` was projected from (`sessions.lineup_revision`), written in the SAME fenced step as the line-up, never inside it. Redis-only moments have none. Dies with the session
- `s:{CODE}:r:{IDENTITYID}:{WINEID}` — per-rating JSON (score, flavors, notes, `at` = the mirror token, equal to `ratings.mirror_at` for logged-in raters). Identity-id keyed (`u:<userId>`, `a:<uuid>`, or `d:<uuid>` for a deleted account's tombstoned ratings), never display name
- `s:{CODE}:identities` — hash of identity-id → display name (the participant list)
- `s:{CODE}:tokens` — hash of anon-token → identity-id (used by the resolver)
- `s:{CODE}:lastseen` — hash of userId → ms timestamp of that user's last activity (visit + rate). Read by `/api/me/sessions` to pin a date-less session as "Just visited" for 1h since the user's last touch. Bumped via `bumpLastSeen` (`lib/redis.ts`), inherits the session TTL (dies with it; `touchWithMeta` re-stamps it). Ephemeral by design — never archived to Postgres.
- `u:{userId}:carouselhidden` — **USER-scoped, NOT `s:{CODE}:`** (the one session-related key that isn't session-prefixed): a Set of session codes the user dismissed from the Moments-home highlight carousel (they stay in "All moments"). Must outlive any single session, so it carries its OWN rolling 60-day TTL (refreshed on each `hideCarousel`) instead of riding a session TTL — `touchWithMeta`'s `s:{CODE}:*` SCAN does NOT cover it. `getHiddenCarousel`/`hideCarousel`/`unhideCarousel` in `lib/redis.ts`; auto-cleared on re-engagement (`/visit` + rate call `unhideCarousel`). The "never SCAN-delete outside `s:`/`rl:`" rule: this `u:`-prefixed key is self-TTL'd, never SCAN-swept. **Account-delete reclaim**: `lib/accountDelete.ts` reaches session keys by code only, so any `u:{userId}:*` key needs an EXPLICIT `redis.del` in its post-commit `projectAfterCommit` (carousel-hidden already added) — a new user-scoped key that forgets this leaks past account deletion until its own TTL.
- `s:{CODE}:bans` — Set of banned identity-ids (see `docs/dev/kick-ban.md`)
- `s:{CODE}:kicked` — Set of kicked-but-not-banned identity-ids
- `s:{CODE}:kickv` — Hash identity-id → kick counter (HINCRBY on every kick, `lib/sessionWipe.ts`): `/join` binds a rejoin to the kick it observed in a Redis-only session (the member row's `xmin` does it for a Postgres-backed one), so a paused rejoin never clears a later kick
- `s:{CODE}:shown` — Set of `a:` identity ids: the guests WITHOUT an account who are shown to people looking in (Moment Visibility, `docs/dev/proposals/moment-visibility.md` § 5). 🔒 SADDed in exactly ONE place, the anonymous join's fenced write (`app/api/session/join/route.ts`), when it MINTS the identity, flag or no flag; no rename, rejoin, heal or rebuild adds to it, so a guest who hid is never re-shown. A guest missing from it is counted, never named, so a lost or evicted key hides (fails closed). Carries the roster's TTL; re-stamped and wiped with the other `s:{CODE}:*` keys. Signed-in people's choice lives in Postgres (`moment_privacy`), never here.
- `s:{CODE}:gen` — the publication generation (random token): a rebuild records it under its locks and publishes only while it is unchanged; set by every writer that changes durable state WITHOUT holding the session lock (rate, rate DELETE, bookmark, check-in PATCH), by the wipe and wine DELETE (they delete rating keys), and by every scoped invalidation / account-deletion projection. Rating-key writes are fenced by the writer's own token (`ratingKeyWrite`). Dies with the session.
- `lock:session:{CODE}` — the fenced session lock (`lib/sessionLock.ts`; replaced `s:{CODE}:lock:ban`). Random token, 15 s lease, compare-and-delete release; every holder write is fenced (`WATCH` lock / token check / `MULTI`, or a Lua token check). Outside `s:` on purpose — `touchWithMeta` re-EXPIREs and the wipes SCAN-delete `s:{CODE}:*`. Self-TTL'd, never SCAN-swept (like `lock:native-session-prune`).
- **Better Auth keys (native auth, `lib/betterAuth.ts`)** — BA's `secondaryStorage` writes this same Redis DB, UNPREFIXED: `<sessionToken>` (bare opaque token → JSON session; the Redis-first read copy — see root CLAUDE.md "raw row deletes do NOT revoke"; 🔒 and the converse: `secondaryStorage.get` in `lib/betterAuth.ts` returns a session copy ONLY if its `auth_sessions` row still exists, deleting orphans on sight — a refresh racing a revoke otherwise resurrects the session), `active-sessions-<userId>` (token list), `verification:<identifier>`, and rate-limit keys `<ip>|<path>` (integer counters since BA 1.7; `no-trusted-ip|<path>` when no client IP resolves). Don't add new Verre keys shaped like a bare token or containing `|`, and never SCAN-delete outside the `s:`/`rl:` prefixes. `<sessionToken>` keys carry the native session window as TTL (1 year sliding — `lib/betterAuth.ts` session config), and a Redis miss is served from Postgres WITHOUT re-populating Redis (BA `findSession`, 1.6.15 and 1.7.18; `updateSession` rewrites a copy only if one exists), so an evicted key means DB reads for the rest of that session. The `resolveUser` last-seen bump (`updateSession` with `{ updatedAt }` only, once per 5-minute bucket, budget `rl:native-lastseen:user:<id>:5m`) is the only server-side `updateSession` besides the heartbeat slide. 🔒 Never call `betterAuthServer.api.getSession` server-side without `query: { disableRefresh: true }` — only the HTTP heartbeat may slide (its Set-Cookie is the one the device stores; a server-side slide is invisible to the phone and signs it out early). 🔒 `active-sessions-<userId>` is written on session create/update/delete (every heartbeat slide and last-seen bump reads and rewrites it, unlocked, so it can lose or keep stale entries) and is never read to authenticate; BA's native revokes enumerate Redis copies from it — if it is evicted they miss; the hooks in `lib/betterAuth.ts` answer the native revokes themselves via `revokeNativeSessionsExcept` (Postgres snapshot, token-driven, PG rows survive as retry targets on failure). `lock:native-session-prune` — NX lock (20h) taken by `lib/nativeSessionPrune.ts` so the daily in-process prune of expired native rows runs once fleet-wide; it is the only `lock:`-prefixed key, self-TTL'd, never SCAN-swept.

## NX / XX + `KEEPTTL` — load-bearing (lint-gated)

**`s:{CODE}:meta` and `s:{CODE}:wines` are written `NX` to create (create route, promotion, rebuild) and `XX` + `KEEPTTL` to update (everyone else; the line-up projection's Lua is XX-only by construction).** A wiped or evicted key can never be recreated by a stale writer whatever lock it holds, and `KEEPTTL` keeps an `unlimited` lifespan from being reset by a routine edit. A lifespan change (settings, promotion) is `XX` + a separate fenced `EXPIRE` of every key: `expireSessionKeys(fence, code, lifespan)` (`lib/session.ts`). `touchWithMeta` re-stamps only while meta still reads what it computed the TTL from (compare + EXPIREs in one script, re-read on change), so a touch that raced a lifespan change cannot put the old TTL back. `eslint.config.mjs` errors on any `.set(k.meta(…)|k.wines(…), …)` without `NX`/`XX` in `app/**` + `lib/**` (pins in `scripts/tests/lint-boundary-units.mjs`); a key held in a variable evades it — write these keys inline. For a Postgres-backed session, meta is always written FROM THE RECORD (`metaFromRecord`, `lib/sessionRecord.ts`) ⊕ the cache-only `a:` bits — never a delta on cached meta.

## Session mutation contract (`lib/sessionMutation.ts`) — every durable session writer

`withSessionMutation(code, { redisLock, expectedCreatedAt?, readMeta?, caller?, bumpGen? }, work, projection?)`: (1) the fenced Redis lock when the writer writes a shared-state key (meta, wines, identities, bans, kicked) — busy → `ContractBusy`; (2) `BEGIN` + `pg_advisory_xact_lock(hashtext('session:'||code))`; (3) entry checks INSIDE the locks — lease still ours, meta read + incarnation, the live row `FOR UPDATE`, the caller re-resolved with a FRESH grant (`ctx.caller`, `ctx.callerStatus`); (4) `work(tx, ctx)`; (5) COMMIT; (6) `projection(ctx, result)` after COMMIT — a failure scoped-invalidates (meta DEL if it is still this incarnation + a `gen` bump) so the next request rebuilds; (7) release. A cold cache at entry → rebuild + ONE retry. 🔒 **One incarnation per request:** the admission binds the caller to the snapshot the route opened (`participantOrBanned(code, req, session, opened.meta)` — the grant must match it, else 503), and `expectedCreatedAt` defaults to `caller.incarnation`, so a code deleted and reused mid-request refuses (404) instead of writing into the successor. 🔒 Lock order Redis → advisory → row; never take a Redis lock while holding an advisory lock (account deletion's `'replan'`); promotion (`ensurePromoted`) runs BEFORE a route's own contract (not re-entrant). Every gating decision inside a contract uses `ctx` — a pre-lock check is only an early reject. Map failures with `contractFailure(err, code)` (`lib/sessionRehydrate.ts`): busy → 503 + Retry-After (or the route's 429/409), gone → 404, cold → rebuild then 503, refused → its response.

🔒 **Ordering rule (no cross-store transaction):** a Postgres-backed moment's BOTTLES are record-first (catalogue model change § 8a, `lib/occurrences.ts`): decided on the rows read `FOR UPDATE`, written, `sessions.lineup_revision` bumped by the contract's row lock (`bumpLineup`), COMMIT, then the line-up projected FROM THE RECORD with its stamp (`projectLineup`, fenced, `XX KEEPTTL`); a failed Postgres write fails the request, nothing reaches Redis first. Rating keys stay Redis-first inside step 4 (repaired from the record by the rebuild). DENY-direction cache writes may precede COMMIT (SADD bans/kicked, HDEL a removed identity, stripping role entries, TIGHTENING a visibility flag — settings OR `blind`/`blindForEveryone`/`hideLineup`, AND `showProvenance`, and take the later lineup reveal time). GRANT-direction writes only follow COMMIT (SREM bans/kicked, registration HSETs, adding roles, loosening a flag, the `d:` migration). For `a:` targets and Redis-only sessions the fenced Redis write in step 4 IS the change.

| Writer | Redis lock | Notes |
|---|---|---|
| create | yes, no wait, per candidate code | code CLAIMED under the locks; logged-in: row + host member row + hosted/joined counters in one txn, keys as the projection |
| promotion, rebuild, DELETE, wine CRUD/reorder/reveal/image, reassign, set-role, settings, name, kick/ban/unban/leave, visit, join, heal, re-seeds, anon rename, profile-rename propagation, the line-up refresh | yes | bottle writers are record-first with `bumpLineup` (a NULL revision reconciled first, `reconcileLineup`) and project the line-up after COMMIT; promotion copies the line-up through the shared record insert and stamps 1; rebuild publishes BEFORE COMMIT (fenced, `WATCH gen`) — `rehydrateSession` (`ensureSessionLive` = its status) plans (`planPublish`, reads only; the line-up NX when absent, REPLACE when not stamped with the record's revision) then applies (reconciling a NULL revision first); the operator script's dry run takes the advisory + row lock, NO lease, and writes nothing; DELETE's fenced wipe is in step 4 |
| rate POST / DELETE, bookmark, session-rating check-in PATCH | only when a rating key may be DELETED (rate DELETE, a reaping payload) | always the advisory lock + `bumpGen`; every rating-key write goes through `ratingKeyWrite(ctx, …)` — fenced by this contract's own `gen` token (a stale writer whose backend died is a no-op), and a DEL without the lease throws `ContractNeedsLease` → one re-run WITH the lock; check-in PATCH is `readMeta: false`, owner-admitted |
| account deletion | leases for wipe candidates, taken before BEGIN | one txn via `withSessionLocks`; fenced renew per session; d: migration under a lease after COMMIT |

## Bottle writes: record-first in a Postgres-backed moment, `mutateWines` in a Redis-only one

Catalogue model change § 8a; `lib/occurrences.ts`. Mode is decided by `ctx.row` under the locks, never by the caller's login.

- 🔒 **Postgres-backed (`ctx.row`)**: the RECORD decides. A contract that writes bottles passes `bumpLineup: true` (its row lock bumps `sessions.lineup_revision` in the same statement), calls `reconcileLineup(tx, ctx.row)` first (🔒 **NULL = not reconciled**: a present cache's bottles are copied in strictly and the record's unlisted rows ORPHANED, ratings kept, then stamped 1; never REPLACE a cache from a NULL revision), decides on rows (`lockOccurrence`: ownership and "concurrently deleted" from the row), writes through the helpers (`insertOccurrence` INSERT-only, `relinkOccurrence` for a re-link's whole snapshot, `editOccurrenceNotes` for the fields an edit sent, `renumber`), reads `recordLineup`, and projects it after COMMIT (`projectLineup`). No best-effort mirror: a failed write fails the request. Every statement that sets `style` keeps colour / sparkling derived from it (the backfill re-run's rule). Writers that cannot reconcile (account deletion, operator scripts) `bumpLineupRevision`, which leaves NULL as NULL. 🔒 Every writer is listed in `scripts/check-wine-writes.mjs` (CI census, own negative control).
- **Reads**: `servedLineup` (`lib/sessionRoute.ts`) compares the cached stamp (`openSession`'s MGET) with the record's revision (the caller's grant read; a guest pays one read, checked against the opened incarnation) and, on a mismatch, `refreshLineup(code, expectedCreatedAt)` re-projects under the contract. 🔒 A KNOWN mismatch never serves the cache (a hide whose projection died would show a hidden bottle): a busy or failed refresh serves the record's line-up read directly, else 503; the cache is served only for an unreconciled moment or a failed state read. Lists and enrichment never do.
- **Redis-only**: `mutateWines(fence, transform)` (`lib/session.ts`), inside a contract holding the session lock. On an isolated connection it WATCHes the lock + the lineup, checks the token, and writes `SET XX KEEPTTL`; 🔒 an absent lineup is a REJECT (`ContractCold` → rebuild), never a create. **Never `redis.set(k.wines(...))` directly.** The `transform` **must be pure** (it re-runs on each retry); return a `MutateReject` (`{ reject }`) for current-state validation. The client-id rule holds here too (an id already in the cached array: the same adder's retry, else 409; an id the record holds anywhere: 409).
- 🔒 **Ids are client-minted** (`isClientOccurrenceId`, nanoid shape) and a create is INSERT-only: a retry that finds its own bottle answers an identity-free `{ id, alreadyAdded }`. **Photos have their own call** (`PUT/DELETE /api/session/:code/wines/:id/image`): refused in a Redis-only moment (403), uploaded under a fresh key before the contract, the new object reclaimed (awaited) when the write fails, the replaced one after COMMIT (`lib/occurrenceImage.ts` is the seam).
- Named exception: `scripts/rekey-session-images.mts` moves an old photo URL with a compare-and-set of `wines.image_url` (`= old`) inside the contract, bumps, and projects.

## Catalog writes go through `lib/catalogWrite.ts`; catalog matching goes through `lib/catalogSearch.ts`; catalog READS go through `lib/catalogEntries.ts`

Same chokepoint pattern as `mutateWines` above and `lib/identityStore.ts` — the invariants live in root CLAUDE.md § Wine catalog; this is where they're implemented.

- **Never call `prisma.producer.create` / `wineProduct.create` / `wineVintage.create` / `productProducer.*` from a route.** Route them through `createProducer` / `createProduct` / `createVintage`. Phase 4 must append a change-journal event **in the same transaction as every catalog mutation** ("a single mutation path that skips the journal reintroduces the silent-omission class the journal exists to eliminate"), and one helper is what makes that a single edit rather than an audit. Corollary: prefer passing a `tx` — a mint that runs outside a transaction cannot carry a journal append. `product_eans` has no application writer yet (import-owned); when phase 4 adds one, it goes here.
- 🔒 **A `WineProduct` can never be created in one statement.** A deferred trigger rejects a lead-less product at COMMIT, so the product row and its `product_producers` lead row must commit together — `createProduct` does this. A bare `prisma.wineProduct.create()` always raises `has no lead producer`. That's the invariant working, not a bug (`prisma/CLAUDE.md`).
- 🔒 **Nothing in either module may become a find-or-create.** An entry is created DISTINCT; the fuzzy match only ever produces suggestions for a human. Auto-selecting the top hit is the model that got PR #82's schema rejected.
- 🔒 **Every user mint writes its review item** (`catalog_review_items`, reason `user-mint`) in the mint's own transaction (`recordUserMint`, inside the three helpers): the fence opens before the review queue, and `provisional` alone is not that record. A mint with no user (import, fixture) writes none; a rolled-back mint takes its item with it. `tx` stays REQUIRED on all three (the compiler enforces it).
- 🔒 **Bottle writes link through `lib/catalogLink.ts`** (catalogue model change step 4): `prepareLink` before the locks (shape, the guest's one fixed refusal, the kill switch, the budgets; it never reads the target bottle), `applyLink(tx, …)` / `applyRelink` (edits) inside the writer's transaction AFTER its power decision: 🔒 a pick is resolved there (`resolveCatalogLink(…, existing, tx)`: against the bottle AS LOCKED, on the writer's own connection; review r1/r2: resolved earlier it was an oracle on someone else's blind bottle and wrote stale grains back); on a bottle hidden from the caller (Blind for Everyone) a pick must name both the wine and the year (`PICK_WHOLE`) and a `create` is refused (`CREATE_HIDDEN`); a re-link `create` the bottle already carries (this caller's own mint, every field equal: `isReplayedCreate`) mints nothing (`mintEntries(body, userId, tx)` for a create: the add flow joins the CALLER's transaction, and branch 2's check-then-insert is serialised by an advisory xact lock on (product, year), since a lost race can't be caught inside an outer transaction; then the entry read for the snapshot). 🔒 The snapshot (name, producer, year text, `style` token derived from the pair, colour, sparkling, abv, grape, region, origin) is written ONLY at link time (`relinkOccurrence` / the inserts), never from a body; the bottle's own fields through `editOccurrenceNotes`, only those sent. A typed abv lands on the vintage minted with it, else on the product (ruled 2026-11-20).
- 🔒 **ONE merge resolver** (`lib/catalogEntries.ts`: `resolveEffectiveIds`, `loadEntries`, `linkableLink`, `productVintages`): every catalogue read that shows or counts something follows `links_to` through it (spec § 8b; a forgotten resolution fails silently). `loadEntries` is one statement when nothing is merged (products + lead producers + vintages in a UNION ALL), plus one per merged grain. ⚠️ After a PRODUCT merge a bottle's vintage stays a child of the merged-away product, so an entry's (productId, vintageId) is not always a linkable pair: a copied link goes through `linkableLink` (the survivor's same year, else product grain). CI census: `scripts/check-catalog-reads.mjs` lists every raw catalogue read outside this module and `lib/catalogSearch.ts`, each with its reason, own negative control.
- 🔒 **Cravings go through `lib/cravings.ts`** (catalogue model change § 5, step 5): every bookmark read (`ownerCravingsSql`, `cravingHiddenSql`, `viewerSeesSql`: a craving hidden for its OWNER is left out, never a blind row) and every crave write (`saveBottle` / `unsaveBottle` per bottle, `removeCraving` by id, `beforeBottleDelete`, `afterRelink`), and the per-viewer `saved` flag (`savedFlags`, one statement per line-up or feed page). 🔒 A save of a bottle hidden for the caller stores ONLY a `blind_saves` row, the same work whatever the wine (no craving, no bookmarks id, step 5 review r1), and counts as a craving once the bottle shows for its saver: every read of someone's cravings goes through `ownerCravingsSql` (real cravings + those saves, one row per wine), never `bookmarks` alone. The caller decides "hidden" by its surface's rule (the live `bottleHiddenFor` in a moment, the outside rule on a post) BEFORE any other refusal. Matching two links is merge-aware through `lib/catalogEntries.ts` (`sameWineSql`, `productAliasesSql`, `effectiveProductSql`), never an equality of stored ids. Writes for one user serialise on `cravings:<id>`, always after any session lock.
- 🔒 **`resolveCatalogLink` is the only sanctioned way to accept `productId`/`vintageId` from a request body**, and it returns ONE generic message for every denial — distinguishing "unknown id" from "owned" / "rejected" / "wrong product" turns it into a catalog classifier, and these paths are reachable from the ordinary wine + check-in routes, i.e. outside the release fence.
- 🔒 **Merge tombstones RESOLVE to their survivor — they are not hidden.** `linked` rows are matched and then resolved (transitively, visited-set + depth cap) at BOTH grains, and product results report the **effective** producer's id and name. Excluding tombstones instead made a merged alias unfindable, and selecting the stored producer advertised a row already merged away. ⚠️ Public release no longer waits for phase 3 — the gate is OPEN by default with the model-change code (`lib/catalogGate.ts`; `CATALOG_PUBLIC_ENABLED=false` is the kill switch), so publicly-writable *provisional* entries exist before any curator UI does. Tombstones only appear once phase 3 ships the merge machinery, since nothing writes one before then.
- ⚠️ **Alias resolution must never become a catalog-wide scan.** Expressing it as a recursive CTE over the whole `producers` table — joined into every product search, including the unscoped path that doesn't use it — measured **3,252,182 blocks / 517 ms** at 60k producers × 60k products, versus ~1,600 blocks / 83 ms for the current shape (a selective search went 0.16 ms → 60 ms). Resolve only the chosen producer's alias GROUP (`producerAliasGroup`, index-served off `producers_links_to_idx`) and keep two distinct SQL shapes rather than one query with a nullable parameter — `($n IS NULL OR …)` leaves the join in the plan when unused. 🔒 The suite guards this **structurally** (§ 1b): the cost is superlinear, so a CI-sized fixture cannot catch it by measurement — a mutation reinstating the CTE cost only ~170 blocks at 30k rows and passed a block-ceiling assertion.
- 🔒 **Search orders by a GiST KNN distance** (`trgmOrderSql` — `col <->> catalog_fold_v1($1)`), with ONE definition shared by the runtime queries and the query-plan assertion in `scripts/tests/catalog-addflow-integration.mjs` § 1 — inlining it back into the queries silently disarms that test. ⚠️ **Operator and operand ORDER must match** — `column <->> query` and its commutator `query <<-> column` both plan an Index Scan (~4.9 ms); the mismatched pairings `column <<-> query` / `query <->> column` seq-scan the whole table (~116 ms over 60,001 rows) while returning correct rows. `<<->` is the declared commutator of `<->>` (pg_operator), so it is NOT a forbidden operator — it is usable only with the query on the left. Same operand-order trap as the GIN `<%`/`%>` pair. `<->>` is exactly `1 - word_similarity`, so ranking and typo tolerance are unchanged. **Why the swap:** `<%` at threshold 0.3 is not selective — candidates scale 1:1 with the catalog (a "selective" multi-word name still admitted 8.5% of a 300k catalog), the heap recheck dominated, and latency grew linearly (34 ms at 60k → 352 ms at 300k, with 15/50 concurrent searches failing on pool timeouts). The 0.3 threshold is now a **post-filter** on the rows KNN returns (`limit × 3`, ≤60, plus the exact matches), which also removed the `SET LOCAL` GUC and with it the interactive transaction that pinned a pool connection per search. **The GIN indexes are REPLACED by covering B-trees**, not kept: a trigram index is the wrong structure for `=`, and measured on the REAL query the planner chose GiST (0.544 ms / 130 buffers) over a bare B-tree — only `(name_folded, id) INCLUDE (status)` wins on its own, as an Index Only Scan with zero heap fetches (0.125 ms / 4 buffers). Nothing issues a `%`/containment query, so GIN had no live consumer.
- 🔒 **Ties are re-ranked in the module, never in the ORDER BY** (`rankSql` / `byRank`: exact folded match, then the score, then two-way `similarity()`, computed in an outer select over the limited rows; the two columns never leave the module). `<->>` scores every name that contains the query as a full match, so without it the order among ties was the index's. The producer statement has a second arm for EXACT folded matches on the covering B-tree, spelled as a range (`>= f AND <= f`: for `=` the planner prices GiST lower as soon as part of the table is not all-visible), so an exact name is offered even when more than 60 names tie with it. And **merge resolution runs only when a returned row or its producer is `linked`** (anything else resolves to itself by the `links_to` CHECK): the trigram producer search (`similarProducers`) and an unscoped product search are ONE statement, a scoped one TWO (`producerAliasGroup`, then the search). Each statement is a round trip plus app CPU on a fractional-core instance. Both pinned by § 2c of `scripts/tests/catalog-addflow-integration.mjs`.
- 🔒 **Two query families in the one matcher since step 7b** (the module header). EVERY-WORD (add time, the people who pick): `searchBottles` (the app's one field, `kind=bottle`) and `searchProducers` ("Add Wine to Catalogue"'s producer field and the web's producer step; ⚠️ TWO statements since 7b, step 1 recorded ONE, deliberate). SIMILARITY (trigram KNN): `similarProducers` (the old `searchProducers`, for phase 3 / 4 duplicate finding, review scope), `searchProducts` (a chosen producer's wines), `browseProducts`, `findProducerByExactName`. Every-word rules (Simon, 2026-11-21): every typed word matches in the producer, the wine name or the region, any order, the last as a prefix, small typos (same first letter, OSA ≤ 1 from 4 letters, ≤ 2 from 8); nothing fits → an empty list ("Add Wine to Catalogue"); filler words (`SEARCH_FILLERS`, folded) optional; a typed year is detected (the ONE range, `isCatalogYear` in `lib/catalogWrite.ts`) and CARRIED, never required; "nv" a boost; over 16 words or 200 characters REFUSED (`tooLong`), never cut. Plan + review trail: `.local/catalog-model-change/step7b-plan.md`.
- 🔒 **The every-word search reads Verre's own search docs** (`catalog_search_docs` per product: the stored words of its lead producer, that lead's effective survivor when it is a tombstone, its name and region, plus `tsv_name` / `tsv` tsvectors; `catalog_search_producer_docs` per producer; `catalog_search_words` + a trigram GiST for typo lookups), built by ONE tokeniser for docs and queries (`catalog_search_words_v1`, parser-free; migration `20261121180000_catalog_search`). Two statements per search (words, candidates), four on an empty answer (the fallback for a typo that is another doc's word), plus merge resolution only for tombstones. The candidates statement is TIERED (the year as a word, all words incl. fillers, the required words on `tsv_name`, then with the region on `tsv`), each arm LIMIT 401 with live eligibility INSIDE the arm, one outer LIMIT 401; `more` = the server stopped early. Merges resolve at READ time (a tombstone's own doc matches, `mapProductMatches` maps it, the matched row's rank and year decision win the de-dup). ⚠️ The exact word lookup is spelled as a RANGE (`>= w AND <= w`): for `=` the planner chose the trigram GiST over the primary key (1.3 ms a word instead of 0.02, dev DB 2026-11-21). ⚠️ The candidates' words travel as ONE text column (`wordsColumn` / `splitWords`), not four `text[]`: decoding the arrays of 401 rows was most of a broad search's app CPU (4.78 → 1.33 ms in-process; on a 1/8-core container a broad search costs about 9 ms of CPU against about 4 for a selective one, sandbox 2026-11-21). 🔒 **The word list never decides whether a wine is found** (a typed word is always its own alternative), only whether a typo lookup runs, so it is kept loosely: `ndoc` counts LIVE docs only (add-time statuses or a tombstone, shared scope, the lead not rejected; 0 for a word nobody live holds, never deleted), the typo lookup skips `ndoc = 0` words and ranks equal typos by `ndoc` (junk words minted next to "riesling" never crowd it out). 🔒 A product whose lead producer is REJECTED is never offered (inside every arm, and the effective producer after resolution); an archived producer's wines stay findable. A half-typed year as the last word ("…20") is optional while typed; a number typed last is a prefix; when nothing but fillers is typed only the FILLERS are searched for ("nv" and a half-typed year stay boosts); `kind=producer` answers `exact` (a listed producer carries exactly the typed name, as `catalog_fold_v1` folds it: "Strass" = "Straß"), which the app's "Add Producer" reads instead of folding names itself; `more` is also set when the ranked list is longer than what is sent. `kind=producer&similar=1` (the website's producer step only, ruled 2026-11-21): when every word finds nothing, the trigram list (`similarProducers`) instead, so a label scan's extra words don't lead to a duplicate producer. Named residuals (security review 2026-11-21): a misspelling minted as a provisional entry's word ("Reisling") is known, so it gets no typo lookup while that entry is live, unless the first pass finds nothing (the empty fallback then corrects it while 50 or fewer docs hold it), and after a curator rejects the entry its words count 0; more than 30 junk words nearer than the real one can still push it out of the KNN; a typed word's latency tells whether some hidden entry holds it. Pinned by `scripts/tests/catalog-bottle-search.mts` (CI).
- 🔒 **The docs are kept current by OUR writes, in the same transaction as the row they describe** (`lib/catalogWrite.ts`: `createProducer` → `indexProducer`, `createProduct` → `indexProduct`, `purgeProduct` deletes the doc), plus the rebuild after every catalogue load (`scripts/rebuild-catalog-search.mts`, whose dry run is the DRIFT REPORT; the rebuild is the migration's `@recipe:catalog-search-build`, read from the file by `scripts/lib/catalogSearchRebuild.mjs`), plus a CI census (`scripts/check-catalog-writes.mjs`: every write of `producers` / `wine_products` / `product_producers` / the three search tables outside `lib/catalogWrite.ts` is listed with its reason). A mint's NEW words are added AFTER its COMMIT (`publishSearchWords(tx)`, called by every transaction that can mint: the session mutation contract, the check-in POST and PATCH, `mintEntries` on its own transaction), best effort, sorted, NOT awaited (inside the contract it must not hold the lease before the projection), under the SHARED catalog-search lock (never inside a rebuild, which could zero a just-published word or deadlock with its two word passes) and a 2 s `lock_timeout` (during a rebuild it gives up; the words wait for the next one). Only new or zero-count words reach its conflict path, so a common word's row is never locked by a mint. "live" in `ndoc` is judged on the STORED lead (a tombstone lead whose survivor is rejected still counts: no such rows before phase 3). 🔒 **THE ROW RULE** for every doc write (`lockForSearchDoc`), in ONE order taken BEFORE any source mutation: (1) the producers involved (leads + their effective chains) in id order, FOR UPDATE for a row the writer changes, FOR SHARE otherwise; (2) the products involved in id order, FOR NO KEY UPDATE; (3) the source rows; (4) the doc in a NEW statement. A chain that moves while its rows are being locked (a merge, phase 3) would need a row that sorts before one already held: `lockForSearchDoc` throws `SearchLockRetry` instead, and the caller restarts its transaction (Codex 2026-11-21). A mint takes the adder's user row FOR KEY SHARE first (an account deletion of the adder holds that row, then sets its producers' `added_by` NULL: taken after the producer lock, the two deadlocked), then its lead's FOR SHARE (its product is new). 🔒 **Phase 3's writers follow it and re-index**: a producer rename refreshes its own doc and every product doc whose lead RESOLVES to it (its reverse alias closure, the bounded walk of `producerAliasGroup`, computed once per group); a producer merge or unmerge refreshes the loser group's product docs (their effective producer changed); a product rename / region / lead change refreshes that product's doc only (no doc copies another's words). Each of them ALSO takes `pg_advisory_xact_lock_shared(hashtext(CATALOG_SEARCH_LOCK))` as the FIRST statement of its transaction (the rebuild takes the exclusive form first; an import that ends with a rebuild takes the exclusive one at its entry), with a `lock_timeout` (a rebuild runs about 10 s on the full catalogue). Tests for chained merges, unmerge and alias fan-in land with phase 3's writers. Paused-schedule pins for the rule: `catalog-bottle-search.mts` § 7.

## Moment Visibility is read and written from the record (`lib/momentSettings.ts`)

`docs/dev/proposals/moment-visibility.md`; dark behind `MOMENT_LOOKIN_ENABLED` (`lib/momentGate.ts`, no staff bypass).

- 🔒 **The seven columns (`visibility`, the three switches, the link's `link_version` / `link_active` / `link_since`) are NEVER mirrored into the cached meta.** `SessionMeta`, `metaFromRecord`, `sessionMetaToColumns`, the settings PATCH, create, promotion and the rebuild don't know them. A meta cached before the deploy has no such fields and lives up to a year, so "absent from meta" would read as "feature off" on exactly the old moments that just opened. Readers go to the row: `readMomentSettingsByCode` (the GET), `readMomentSettings(tx, ctx.row.id)` inside the contract (`ctx.row` does not carry the columns).
- 🔒 **NULL reads as closed or off** (`fromRow`): a tombstone's columns are NULL, and a look-in read must never open on a value it can't parse.
- 🔒 **`host_user_id IS NULL` freezes a moment**: `widens(current, patch)` refuses any change that opens one of the four wider (narrowing stays allowed), and `linkAvailable` is false, so a guest-hosted moment stays closed and a moment whose host deleted their account keeps what it had. Account deletion ends that moment's link in the record when it tombstones the host (`lib/accountDelete.ts`: off and a new version), so the shared token is dead by itself, not only behind a reader's hostless check. Guest-hosted rows are closed by the database, not by code: the trigger `sessions_guest_hosted_closed` (`prisma/CLAUDE.md`), so promotion writes nothing about it.
- **Writers** (`lib/momentSettingsRoute.ts` `momentSettingsWrite`, shared by the visibility PATCH and the look-in-link POST): inside the session mutation contract with `redisLock: false` (they write only the row); the power is decided under the locks from `ctx.caller`. 🔒 Signed-in only: a `u:` caller with a grant that makes them host or cohost. A guest cohost's role lives only in the cache and opens nothing.
- **The link** (`lib/momentLink.ts`; the derivation refuses anything that is not a public id and a version from 1 up): `<base>/l/<publicId lowercase>.<token>`, token = the first 16 bytes of `HMAC-SHA256(MOMENT_LINK_SECRET, "verre-moment-link-v1" ‖ 0x00 ‖ PUBLICID ‖ 0x00 ‖ link_version)`, compared with `timingSafeEqual`. Nothing secret is stored. 🔒 The version only ever goes up (`writeLinkAction`: Reset, and Share on a link that is off; Off never touches it), so turning a link back on never revives an older one. 🔒 The secret fails closed (absent or under 32 characters → no link anywhere, no fallback). 🔒 The token never enters meta, a cache, a log line or an error report.

## Identity resolver (`lib/identity.ts`)

`resolveIdentity(code, req, session)` returns `{id, displayName, kind}` from one of three sources, or `null` for unauthenticated callers:

- NextAuth session cookie (`__Secure-authjs.session-token`) → `kind: 'user'`, `id: 'u:<userId>'`
- `x-vr-anon-token` header against `s:{CODE}:tokens` hash → `kind: 'anon'`, `id: 'a:<uuid>'`
- Otherwise → `null`

**Identity is never read from the request body.** All authorization checks compare on `id`, never on display name.

`isValidIdentityId` also accepts `d:<uuid>` — the tombstone identity account deletion gives a deleted user's ratings in one session. It is a TARGET only (host kick-delete); no cookie or token resolves to one, and ban / kick-keep / brought-by reassignment reject it (`isTombstoneIdentityId`).

`ensureMemberRow(tx, row, userId, { clearKick })` (`lib/sessionMember.ts`) is the one writer of the durable member row for `/visit`, logged-in `/join` and logged-in `/rate`, inside their contract: 🔒 the role comes from the RECORD (`'host'` iff `host_user_id = me`, else `'taster'`) — a cached `coHostIds`/`providerIds` entry becomes a role only at promotion; create-only; joined-counter bump on insert; `clearKick` only for the explicit `/join`. No live row → no member row (codes recycle; B's migration deleted the orphans).

`participantOrBanned(code, req, session, opened.meta)` returns `'ok' | 'banned' | 'kicked' | 'invalid' | 'unavailable'` with an `AuthorizedIdentity` (`lib/sessionGrant.ts`): for a `u:` caller of a Postgres-backed session the RECORD decides (grant read — member, rating author or strict host; minus kicked/banned), a Redis ban still denies first, a missing roster entry is HEALED (`healRegistration`, fenced, 500 ms) and a missing ban/kick entry RE-SEEDED (`reseedRemoval`). `resolveAuthorized` is the same grant without the participant gate — so it folds a CACHED ban into the grant, and the privilege helpers (`isHostByIdentity` / `isStrictHost` / `isProvider`) grant only while `grantStatus(grant) === 'ok'`: a role held by a kicked or banned user grants nothing (set-role also refuses a non-taster role for a removed target, 409). Both take the opened snapshot: the grant — or, without one, the cache that admits — must be that incarnation, else `'unavailable'`. `authRemoved()` / `authInvalid()` live in `lib/authResponses.ts`.

🔒 **List and enrichment reads never rebuild** (`/api/me/sessions`, `lib/sessionFeedWines.ts`, the profile lists): only opening one moment does. Outside a moment a bottle follows ONE SQL rule (`lib/outsideView.ts`): a blind moment's unrevealed bottles auto-reveal once it is over by its RECORD dates (the SQL twin of core `momentIsOver`, on `MOMENT_DEFAULT_SPAN_MS`) — never because the cache is gone; a hidden line-up is left out until its reveal time.

## Per-device sessions (logged-in revocation gate)

Logged-in sessions are gated per-device via the `user_sessions` table (one row per credential login). The signed JWT carries an opaque `userSessionId`; the `auth.ts` `jwt()` callback looks up `user_sessions.revokedAt` on **every authenticated request** and strips identity on a revoked/missing row. This replaced the never-written `users.tokenVersion`. Full design + as-built deviations: `docs/dev/proposals/auth-sessions.md`.

- 🔒 **SECURITY — never cache `auth()`.** The revocation gate is only as fast as the next request that hits Postgres. **Never wrap `auth()` in `unstable_cache`, React `cache`, or a `revalidate`-tagged fetch** — any cache TTL becomes a window where a revoked cookie still resolves, which IS the security hole. The DB lookup must run every authenticated request, same cost as the old `tokenVersion` read. (The proxy, `proxy.ts`, deliberately never checks revocation: on `/me` it runs its own NextAuth instance from the lightweight `auth.config.ts` (JWT signature only), never the full `auth.ts`; on `/api/*` it never runs NextAuth at all (that would append a re-issued cookie to every API response) and only decodes the cookie with `next-auth/jwt` `getToken` (no database, no cookie set) for the old-tab bounce, plus the version floor (`lib/clientVersion.ts`); public-user-ids § 6. The real gate is the Node-runtime `auth()` in the `/me` layout and every `/api/me/*` handler. Don't move a Prisma call into the proxy or `auth.config.ts`. Since Next 16 the proxy runs on the Node runtime, so the build no longer fails if you do; the import allowlists on `proxy.ts` (next-auth, next-auth/jwt, @/auth.config, @/lib/clientVersion) / `auth.config.ts` / `lib/clientVersion.ts` in `eslint.config.mjs`, run in CI by `check-lint.yml`, are the tripwire now.)
- **`lastSeenAt` is self-only.** Queryable only via `WHERE userId = $self` (the `GET /api/me/devices` path). No analytics / other-user / aggregate surface. Stored bucketed to 5-min wall-clock edges (the value at rest is the bucket *start*, not the request time) so an exfiltrated DB can't reconstruct precise activity timelines. `createdAt` stays precise (one-shot, useful for disambiguating same-label devices).
- **`userSessionId` is JWT-only**, like all identity — never read it from a request body/header. Its native counterpart, `nativeSessionId` (the caller's own `auth_sessions` row id, set by `resolveUser`'s Better Auth branch), is likewise server-only: never serialized into a response, and never the session token. At most one of the two is set. The password re-auth on cross-device/revoke-all DELETEs goes through `lib/verifyPassword.ts`, which charges the shared `rl:account` counter (see `app/api/CLAUDE.md` shared-counter pattern).
- **Geo labels (`lib/geo.ts` `resolveGeoLabel`)** turn a login IP into a country name for the device row. **Fully in-process, best-effort, never throws**: the IP is resolved against binary lookup tables on local disk and is NEVER sent off-server (no API/WHOIS) and never persisted (only the country label is stored). The tables are delivered at boot (`instrumentation.ts` → `lib/geoData.ts` `ensureGeoData` downloads them from S3; on a cold start it background-seeds S3 then polls to self-heal this instance without a restart; a weekly `refresh-geo-data` scheduledJob in `.deploio.yaml` regenerates + uploads them). If the files are absent (cold start / download not finished) every lookup returns null → "Unknown location" — so a lookup before boot-download completes is harmless. Don't add a network call to this path. Full delivery story: `docs/dev/deployment.md` + `docs/dev/proposals/auth-sessions.md`.

## Defensive helpers (apply on every state-changing API route)

- **`lib/csrf.ts` `isSameOrigin(req)`** — origin/referer check. **First guard on every POST/PATCH/DELETE/PUT.** Allows same-origin + origins in `SERVER_ACTIONS_ALLOWED_ORIGINS` env. See `app/api/CLAUDE.md` "Origin guard" for the rule.
- **`lib/parsePathId.ts`** — strict path-segment-to-positive-int parser for the NON-user serials on the wire (post ids, `ba:` device rows). **Use this, not `Number(params.id)`.** Rejects leading zeros, scientific notation, percent-encoded whitespace (`1%0a`, `1%20`), and other URL-canonicalisation tricks that could skew rate-limit keys. 🔒 A USER id in a path, query or body is a public id: `lib/publicIds.ts` `parsePublicIdParam` / `parseWireIdentity` (format only, an integer is malformed → 400), then `userIdForPublicId` / `internalIdentity` where today's code meets a nonexistent target (after the limiter and the role gates). Outbound: `publicIdsFor` / `wireIdentityMap` / `metaToWire` (an allow-list, `lib/sessionState.ts`); a miss is DROPPED. Tag arrays: `parseTagList` (any malformed element → 400 for the whole request, resolved before the transaction).
- **`lib/textSafe.ts` `scrub(s)`** — strips C0 control chars + bidi overrides + zero-width chars. **Apply to every free-text field from a request body before DB write.** NULL bytes 500 with P22021; RTL overrides spoof display names in feeds; zero-width chars enable lookalike attacks.

## Rate-limit helpers (`lib/rateLimit.ts`)

- `peekRate(key, limit, window)` — check without incrementing. For paths that must not pollute the counter on success (login-precheck, no-op visibility PATCH).
- `checkRate(key, limit, window)` — atomic check + increment. The default for any limited endpoint.
- `peekRates([...])` / `checkRates([...])` — multi-window batch (e.g. login: 10/min + 20/h + 100/10min/IP all checked together).
- `formatWait(seconds)` — humanizes "3 minutes" / "45 seconds" for 429 response bodies (callers write the "in").
- `reserveMiss(seenKey, counters, …)` / `settleMiss(…, keep)` — the wrong-code budget as ONE atomic RESERVATION taken before a moment is opened (a seen marker → free; a counter at its max → 'spent', nothing incremented; else INCR all), settled after the open (absent → keep + set the marker, a duplicate that lost the race refunded; live → refund, never below 0). A read first and a charge after the open let a parallel burst read "not spent" on every request. `chargeMissOnce` is the one-step charge for a caller admitted on a spent budget whose moment turned out absent. Used only by the entrance gate (`lib/sessionRoute.ts` `openSessionCharged`). `refundRate(key)` gives back one `checkRate` charge (guarded, never below 0) for a reservation that did not go through or was refused (the join POST's guest cap); never on a success. There is no `resetRate` any more: a budget a success resets is a budget one valid code makes unlimited.
- `getClientIp({ headers })` — takes anything with `headers.get` (a `Request`, or `{ headers: await headers() }` in a server component, the join page).

Per-endpoint usage patterns (which helper for which route, shared-counter pairs): see `app/api/CLAUDE.md`.

## Usernames go through `lib/username.ts`

The chokepoint for `users.username` (`docs/dev/proposals/usernames.md` § 8), the `mutateWines` / `identityStore` pattern. CI census: `scripts/check-username-writes.mjs` (`check-identity-writes.yml`) compares every write site it finds with an expected list (this module, the web register's insert, two wire-object assignments) and runs its own negative control first.

- `changeUsername(userId, name, { skipQuota? })`: ONE READ COMMITTED transaction: the user's row `FOR UPDATE` (two changes by one account serialise, so the quota can't be raced), stop if unchanged, the quota (5 counted changes per rolling 90 days; a first choice from NULL is free, switching back counts, `skipQuota` is the operator's rename; `blockOld` turns the old name's hold into a block for everyone with no end date, the moderation rename), `tx.user.update`, a `username_changes` row, old change rows dropped. A refusal rolls back: no quota spent. Returns `ok` / `taken` / `quota` / `not-found`.
- 🔒 **Every write of `users.username` is a MODEL call** (`tx.user.update`, `tx.user.create`), never `$executeRaw`: a taken name (the unique index) and a HELD one (the trigger raises the same SQLSTATE 23505) both come back as `P2002` through a model call, but as `P2010` carrying the original code through a raw statement. `isUsernameConflict(err)` recognises both shapes.
- 🔒 **Never inside a transaction above READ COMMITTED**: the hold trigger refuses (its queries must see a hold committed while the write waited on the unique index). Two routes use REPEATABLE READ for other work (`me/bookmarks`, `me/ratings`); neither touches `users`.
- `usernameTaken(name, forUser?)`: THE pre-check (availability route, the PUT's callers, both sign-ups): someone else's live name OR `username_is_held` (the trigger's own SQL predicate, so the two can't disagree). Advisory: the write's answer from the database is the authority.
- Holds are NOT here: they are triggers on `users` (`prisma/CLAUDE.md` § Usernames), so the four writers and every delete path are covered. `pruneExpiredUsernameHolds` only deletes expired rows from the daily tick in `lib/nativeSessionPrune.ts` (same lock, its own `try`).
- `userForUsername(name)`: the lookup (canonical name → `{ id, publicId }`); a held or renamed-away name resolves to nothing. The validator and the normalisers (`validateUsername`, `usernameFromPath`, `usernameQuery`, `profileSharePath`) are in `@verre/core` (`packages/core/src/username.ts`).
